# 提交节奏规则与执行纪律 (Commit Cadence)

> **归属与引用：** 本规则由 `/nk-commit` 唯一持有；`/nk-work`、`/nk-debug`、`/nk-compound`、`/nk-close`、`/nk-handoff` 全局统一引用，避免各技能各自制定冲突的提交标准。

---

## 一、为什么需要明确的提交节奏

在 AI 编程的实际协作中，缺乏约束的 Agent 容易产生碎片化提交（例如修改代码一个 commit、单独为标记进度发一个 commit、更新 current.md 又一个 commit）。这会导致 Git 历史被零碎的状态记录淹没，增加排查历史和回滚的成本。

NexusKit 的核心原则：**提交单位是“一个经过验证的变化”，文档随代码原子化入库。**

---

## 二、核心提交节奏规则 (R1 ~ R6)

### R1: 提交单位是“一个经过验证的变化”
* 每一个提交包含：**实现代码 + 自动化测试（或可重现的验证证据） + 配套说明文档**（如 `CONCEPTS.md` 术语更新、Plan 范围修正等）。
* **进度以提交为准**：单元进度的确认以带有单元编号后缀（如 `(U3)`）的验证提交为准（可通过 `git log` 查询），不为了单纯标记进度而修改 Plan 正文；Plan 只在业务范围或技术方案发生实质调整时修改。
* **推荐执行时序**：  
  `编写实现 -> 运行测试并验证通过 -> 同步更新相关文档 -> 一次性原子化提交`
* 代码测试未通过前不提交；不同步将配套文档切碎在不同 commit 中。

### R2: 纯状态改动不单独提交
* 开发过程中中途产生的临时状态变化（如审查记录中标记已修复等），留在本地工作区（unstaged/staged），不单独发起 commit。
* 它们随下一个经过验证的代码提交一起入库。

### R3: 未推送的补记用 amend
* 若上一个 commit 刚刚生成且尚未推送到远端，此时如果仅需要补记该提交对应的状态记录：
  * 仅补充文档而不修改提交说明：`git commit --amend --no-edit`
  * 需要微调提交说明：`git commit --amend -m "..."`
* **“尚未推送”的可执行判断方法**：
  * 运行 `git log @{u}..HEAD`，若输出包含该提交，表明其尚未推送到上游分支；
  * 若当前分支未设置上游分支（upstream），则本地提交均视为未推送。
* 若该提交已经推送到公共远端分支，则遵循 R2，将状态改动随下一个代码提交入库，避免重写公共分支历史。

### R4: 纯文档提交的合法时机
日常开发中代码与文档应同行提交。只在以下三个明确场景下允许发起纯文档提交：
1. **会话结束交接点（`/nk-handoff`）**：一个会话开发完成、准备交接给下一个会话时，更新 `docs/current.md`。交接时若上一个提交是本会话产生的且尚未推送到远端，优先通过 R3 (`git commit --amend`) 将 `current.md` 的更新直接并入上一个提交，连纯文档提交都省去；否则才发起一次纯文档交接提交（每个会话至多一次）。
2. **纯规划会话产出**：发想、需求对齐与技术方案规划（`/nk-ideate`、`/nk-brainstorm`、`/nk-plan`）通常只产出发想记录、Plan 与 `CONCEPTS.md`。
   * 会话在规划后结束：这些产出与 `current.md` 一起，作为该会话交接时的那一次纯文档提交（由 `/nk-handoff` 完成）。
   * 同一会话接着用 `/nk-work` 实施：规划产出留在工作区，随第一个单元的提交一起入库（R2），不单独提交。
3. **版本收尾点（`/nk-close`）**：版本交付完成，提炼知识库并清理生命周期工件时，发起一次收尾提交。
4. **关于 `nk-compound` 的提交时机**：
   * 优先在修复或特性提交之前运行，随代码与测试一同提交；
   * 若代码已提交但尚未推送，使用 R3 (`git commit --amend`) 将沉淀的 solution 文档并入该提交；
   * 若代码已推送到远端，将 solution 文档留在工作区，待下一个交接点或下一次代码提交时一同入库。

### R5: `current.md` 只在交接点更新
* `docs/current.md` 是会话入口，不是实时心跳监控器。
* 仅在**会话结束交接（handoff）**、**外部阻断项发生变化**、或**版本/里程碑阶段跃迁**时才去覆写。常规实施单元进行中不触碰 `current.md`。

### R6: 独立行为变化分开提交，审查记录随最后一个修复
* 若一次排查或任务中包含了多个相互独立的缺陷修复或行为变更，可以分成多个独立的 Git 提交以保持历史清晰。
* 针对这组修复的审查记录（`docs/reviews/*.md`）更新，应当统一附加在**最后一个修复的提交**中，不追加无代码的“更新 review”纯文档提交。

## 三、通用执行纪律 (Universal Execution Disciplines)

所有 NexusKit 技能在执行时恪守以下两条底线纪律：

### 1. 未运行的测试或走查，不记为通过
* 静态阅读代码、无语法报错不能作为功能已验证的依据。
* 必须在终端中实际执行测试命令（如 `cargo test`、`pytest`、`npm test`）或自动化走查脚本，并捕获成功的退出码。
* 若因缺乏环境、依赖缺失或硬件限制而无法运行某项测试，必须在验证结论与 `current.md` 中注明“未验证”，避免误导后续接手者。

### 2. 子代理与主会话的分工边界
* 若客户端环境支持派发子代理（Subagent）：
  * 子代理在隔离工作区执行调查、原型验证或代码编写，产出改动内容与验证证据。
  * **子代理不直接执行 `git commit`**。
  * 所有改动交回主会话（Orchestrator），由主会话核对验证证据、确认符合提交节奏规则后，统一发起提交。
