# `docs/current.md` 规范与维护纪律

> **定位：** 跨会话、跨 Agent 的单一入口（Single Source of Session Truth）。  
> **核心原则：** 记录系统现状、验证证据、阻断项、下一步与所在分支；不记操作流水账，不与 Plan 重复记账。

---

## 一、为什么需要 `current.md`

在个人多 Agent（Claude Code、Antigravity、Codex 等）协作开发中，新会话容易面临冷启动失忆与上下文膨胀问题：
* 若要求 Agent 扫描全量 git log 或历史聊天，会快速消耗上下文预算；
* 若在根目录堆积多份操作日志，信息分散且难以迅速定位当前系统真实能力。

`docs/current.md` 作为常驻单例入口：
1. **新会话快速对齐**：Agent 接手时第一步读取该文件，即可明确“所在分支、当前系统具备什么能力、测试验证到哪一步、下一步做什么”。
2. **阻断项清晰透明**：外部依赖或未决缺陷直接呈现，避免重复踩坑或在未就绪的基础上盲目开发。
3. **工作区状态透明**：当会话交接时遗留有未完成的代码改动，接手会话能立即获知其完成度与验证状态。

---

## 二、标准结构与字段模板

`docs/current.md` 整体控制在 **20 ~ 40 行**，内容直接覆盖更新，不按时间顺序追加日志。

```markdown
# 当前状态

- **所在分支**：`feat/v2-parser`（若为主干写 `main`）
- **版本/里程碑**：v2.0.0-alpha（关联计划：`docs/plans/2026-09-25-parser-refactor.md`）
- **已具备能力**：
  - 完成 AST 核心解析器重构，支持流式 token 输出。
  - 完成基础表达式解析与错误恢复机制。
- **验证结果**：
  - 单元测试：`cargo test parser` 全部通过（42/42 passed）。
  - 集成走查：已在 Linux/Windows 走查样本文件，无内存泄露。
  - *未验证项*：超大文件（>100MB）边界压力测试尚未运行。

## 阻断与已知缺口

- [#102](https://github.com/owner/repo/issues/102)：Windows 下特定编码路径报错，等待复现用例。
- （若无阻断，写：无）

## 下一步

- [ ] 实施单元 U3：实现 `parser/visitor.rs` 默认 AST 遍历器（见 Plan 中 U3 定义）。
- [ ] 针对 Issue #102 构建最小失败复现用例。

## 工作区未提交改动（交接时存在未完成代码时必填）

- **涉及文件/单元**：`src/parser/visitor.rs`（实施单元 U3）
- **进度与状态**：已完成基础结构定义与 Trait 声明，节点递归逻辑尚未编写。
- **验证状态**：未验证，当前代码尚不能通过编译。

## 已排除的方案（可选，记录试过但不可行的做法，最多 3 条）

- 尝试过使用内存缓存解析结果，但超大文件下引起 OOM，改用临时文件流式处理。
```

### 字段说明与分工：
1. **与 Plan 的分工不重复**：
   * **实施单元级进度**：进度以带 U-ID 的提交为准（如 `feat(parser): add ast visitor (U3)`，可通过 `git log` 查询），不在 Plan 内做纯进度的编辑或勾选；Plan 只在业务范围或技术选型发生变化时修改并追加变更记录。
   * **下一步**：直接引用 Plan 中的实施单元编号（如 `实施单元 U3`），保持单处维护。尚无实施单元时（规划会话结束），写技能加产物路径，如 `用 nk-plan 规划 docs/plans/2026-09-25-1030-feat-x-plan.md`；plan 已可实施时写 `docs/plans/2026-09-25-1030-feat-x-plan.md 的 U1`。
2. **验证结果**：客观记录执行过的测试命令与结论。未运行的测试必须明确注明未验证。
3. **工作区未提交改动**：依据 R1，未完成或未验证的代码不应提交入库；而在交接点时，这些代码会保留在工作区。此字段确保下一任接手者完全了解工作区现场，防止误删或误判。
4. **已排除的方案（可选）**：记录本会话或前期已验证不可行的路径及原因，防止后续接手者重蹈覆辙，最多记录 3 条最具代表性的弯路。

## 三、更新时机与提交纪律

遵循提交节奏规则（参见 [`commit-cadence.md`](commit-cadence.md)）：

1. **更新时机（R5）**：
   * **仅在交接点更新**：会话结束（handoff）、外部阻断状态发生变化、版本/里程碑状态跃迁（如版本收尾）。
   * 日常单个实施单元开发中不修改 `current.md`，避免其出现在每一次代码提交中。
2. **中途状态不单独发 commit（R2）**：
   * 若交接前因阻断项变化更新了 `current.md`，改动留在工作区，待交接时或下次代码提交时一起入库。
3. **交接时纯文档提交（R4）**：
   * 在使用 `/nk-handoff` 结束会话交接时，更新 `current.md`，发起该会话的交接提交。提交信息风格遵循项目既有约定（如 `docs: handoff ...` 或 `docs(流程): ...`）。
4. **单例覆盖更新**：
   * 每次更新直接重写对应字段，保持文件简明精炼，不将其作为历史日志追加。
