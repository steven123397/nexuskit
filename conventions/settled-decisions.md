# 已定决策 (Session-Settled Decisions)

> **归属与引用：** `nk-brainstorm`、`nk-plan` 共用本约定；`nk-work` 执行时尊重其标注（见 `nk-work/references/implementation-loop.md` 已定决策规则）。

用于承接用户在当前对话中已经做出的决定，让规划在其基础上推进，而不是重新讨论。标注格式以 [`plan-format.md`](plan-format.md) 第四节为准。

## 判定标准

按决定是否经过检验来分类，而不是看用户语气多笃定。

* **已定（settled）**：对话中提出过取舍、备选或风险，用户在看到这些之后做了选择。按下文两类之一记录来源。
* **指示（directive）**：用户直接断言了一个没人检验过的选择（例如开口就说"用 X 做"）。不算已定。它在所在技能的调研/压力测试阶段接受**一次**质疑，结果作为（带或不带标注的）决定条目写进产物。产物是这次质疑的唯一记录，后续阶段不再质疑第二次。
* **无标注（unlabeled）**：只由 Agent 推断或提议、用户没有参与的内容。作为普通规划输入，不加标注。

对照：用户看到取舍后否决了 A → 已定（`user-directed`）；用户对一句顺带提议说"好的" → 至多 `user-approved`；Agent 提议 X 而用户没有回应 → 不加标注。

**不自我认定。** Agent 不给自己未经检验的提议加标注，也不把简单的同意升级为 `user-directed`。只有用户在对话中的行为才能产生来源标注。

## 两类来源

* `user-directed`：用户在展示过的选项之间或违背选项做了选择（"不，做 X"）。
* `user-approved`：Agent 提议并说明了取舍，用户同意。

之后某次交互中已定决策被改动（提出修改、用户接受），改用 `user-approved`。

## 标注

记录在 Product Contract 的 Key Decisions 条目上（`nk-plan` 中记录在 KTD 上），以内联英文括注：

`(session-settled: user-directed — chosen over <备选>: <一句理由>)`

* `session-settled:` 与 `user-directed` / `user-approved` 是固定写法，便于检索；其余部分自由书写。
* 自成一体：决定、被否决的备选、理由，不看对话也能读懂。
* 不另建文件、不放 frontmatter、不加权重或状态字段。

## 使用规则

* 已定决策不再追问。范围综述中写成 `Carrying forward:` 行，不作为提醒项；提问阶段跳过它。
* 调研在已定决策基础上进行，只能凭证据与之相悖。按严重程度处理：
  * 没发现问题 → 照常推进，不提；
  * 次优但可行 → 按已定推进，在写入产物时于该决定条目附上冲突说明；
  * 使其失效（不可行、做错了东西、有破坏性）→ 停下，向用户说明证据并请其决定。
* 已定标注从不压低缺陷证据：已定做法中发现的真实缺陷或不可行性，照原有严重程度报告。
* 把调研交给子代理时，把已定决策作为范围传入，连同被否决的备选（避免重复调研），并附上固定一句："If you find evidence a settled decision cannot work, report it — do not suppress it."（子代理提示词为英文时原样使用）不要传入支持该决策的论证理由；做对抗性或核实工作的子代理不应看到哪些决策被标为已定。
