# 第 2、2.5、2.6 阶段：方案、范围综述、声明核实

## 第 2 阶段：探索方案

仍有多个合理方向时，依据调研和对话提出 **2~3 个具体方案**；否则直接给出推荐方向。

至少包含一个非显而易见的角度——反转（反过来做会怎样？）、去除约束（如果 X 不是限制会怎样？）、或借鉴其他领域的做法。最先想到的几个方案通常只是同一条轴上的变体。每个方案都要过"反泛化"检验：如果它会出现在这类问题的通用清单文章里，就对照依据档案把它磨得更具体，或者删掉。

**先呈现方案，再评价。** 让用户先看到全部选项，再听推荐——先给推荐会过早锚定讨论。

某个方案的选择满足提问规则第 7 条（`interaction-rules.md`）时，在这里提议一次性原型，不在本技能中展开设计。差异是视觉性的（形状、布局、关系）且不满足第 7 条时，呈现选择前先按 `visual-probes.md` 处理；0.3 把主题标为视觉类、且还没有哪个形状决定问过草图时，在这里问。

合适时加入一个有意提高上限的备选：找出哪个相邻的补充或重新表述最能提升用处、累积价值或持久性，同时不带来不成比例的维护成本。把它作为挑战选项与基准并列，而不是默认项。工作已明显范围过大、或原样请求显然就是正确做法时省略。

Deep — product 层级中，备选之间应在**做什么**（产品形态、参与者集合、定位）上不同，而不是**怎么做**。实现层面的变体属于 feature 层级。

每个方案给出：
* 简述（2~3 句）
* 优点与缺点
* 主要风险或未知
* 最适合的情形

**方案粒度：机制与产品形态，不是架构。** 方案描述写机制层面的区别（"暂停作为规则属性" vs "暂停作为事件过滤器" vs "暂停作为独立实体"）和与产品相关的取舍（与套餐层级的耦合、复杂度、迁移难度）。不写实现细节——列名、表名、文件路径、服务类、JSON 结构、方法名，这些是 `nk-plan` 的事。在头脑风暴阶段提前引入架构，会迫使用户基于有意保持浅层的调研做架构决定。

呈现全部方案后，给出推荐并说明理由。额外复杂度带来真实维护成本时偏向更简单的方案，但不要因为某个低成本、高价值的打磨不是严格必需就拒绝它。

一个方案明显最好、其他备选没有意义时，跳过菜单，直接给出推荐。

相关时，说明选择属于：沿用现有模式 / 扩展现有能力 / 全新构建。

用户选择方案时按提问规则使用单选（推荐项标注 `(Recommended)`）。选择过程中敲定的名称按 `terminology.md` 写入术语表。

## 第 2.5 阶段：范围综述

**动手写综述之前，先读 `synthesis-summary.md`。** 两段式结构（内部三栏草稿 → 对话中的范围综述）、四个综述小节与各自的保留检验、每条的可确认性与详略检验、按规模分档的条目预算与重切规则、反模式、循环修改的处理、用户改道、以及内部草稿如何进入文档正文，都只在那个文件里。下面的 Path A / Path B 只决定**是否**问确认问题，不是综述规范。

在第 3 阶段写入需求阶段 plan 之前，向用户展示范围综述——这是 plan 落地前用户纠正范围的最后机会。它的样子应当像两个产品搭档在写 PRD 前互相确认的内容，而不是全面审计，也不是一句话预告。

**所有规模都运行**，包括 Lightweight。非软件路线跳过。

Path A / Path B 由 `synthesis-summary.md` 依据两个信号决定：是否问过阻塞式问题，以及 0.3 的规模。只有"Lightweight 且没问过阻塞式问题"走 Path A（只宣告，不确认）；其他情况——包括无需对话、但开场内容充分的 Standard/Deep——都走 Path B（完整综述，之后必问确认）。严格按该文件的规则，不凭记忆判断路径或撰写综述。

已定决策在综述中写成 `Carrying forward:` 行，不作为问题或提醒项。

## 第 2.6 阶段：声明核实（在 Path B 等待确认期间进行）

即将写入的 Product Contract 会对仓库做可检查的断言时——"不存在重试逻辑"这类否定断言、对具体文件/配置/依赖的引用、任何规划会以之为基础的内容——在发出 Path B 确认问题的同时，派发一个生成档核实子代理（见 `model-tiers.md`），让它在用户思考时运行。传给它：断言清单（每条一行）、依据档案路径（如有），以及这条指令：直接对照代码库逐条核实——预算约 15 次针对性读取——逐条返回判定：**已确认**（附 `file:line`）、**已驳斥**（附相反证据）或**无法核实**。不要让确认问题等待核实结果。

第 3 阶段使用判定结果：写入前修正被驳斥的断言，把无法核实的标为明确的假设。换一个全新上下文来核实，替代作者自我评分——作者核对自己的断言有锚定偏差，而核实者没看过对话。

以下情况跳过：走 Path A；文档不含可检查断言；非软件路线。不支持子代理，或派发在修正调用参数后仍然失败时，在第 3 阶段写入前于主会话内联核实——1.1 的"先核实再断言"规则无论如何都成立。
