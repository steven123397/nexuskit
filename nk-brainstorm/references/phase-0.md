# 第 0 阶段：续作、分类、规模

## 0.1 续作已有工作

只在有 git 仓库时检查；没有仓库则跳过，继续 0.2。

用户提到已有的头脑风暴主题或文档，或 `docs/plans/` 中有明显匹配的近期 plan（frontmatter 为 `product_contract_source: nk-brainstorm`，且内容仍只有 Product Contract、没有实施章节）时：
* 读取该文档；
* 先与用户确认："找到 [主题] 的需求阶段 plan，接着这份继续，还是重新开始？"
* 继续时，简要说明当前状态，从已有决定与未决问题接着推进，**更新原文件而不是新建**。

同时读取 `docs/current.md`（若存在）了解项目当前状态与待确认事项。

## 0.1b 判断任务类型

关键问题：**这项任务是否涉及构建、修改或设计软件？**——不是看它是否提到了软件话题。

* **软件**（继续 0.2）：涉及代码、仓库、API、数据库，或要求构建/修改/调试/部署软件。
* **非软件头脑风暴**（读取 `universal-brainstorming.md` 并按其执行，它替代 0.2–4 阶段）：没有上述软件信号，且用户想在非软件领域探讨、决定或思考某件事。非软件路线不写 `docs/plans/` 下的 plan；`interaction-rules.md` 的原则与提问规则照样适用。
* **都不是**（直接回答，跳过所有阶段）：简单求助、报错信息、事实问题或单步任务。

**"要不要采用 X"也是软件决策。** 权衡是否为本项目**采用 / 切换到 / 替换为**某个具体的外部技术、库、模式或平台，即使只点名了工具，也按软件处理。这类问题的核心是判断，不是描述要做什么，处理方式：
* 以本项目的证据为依据（适配度、迁移成本、是否值得），把"维持现状"作为一个正式备选；
* 在第 2 阶段给出明确的推荐结论和理由，而不是罗列中立的介绍；
* 结论是"采用"时，再继续界定采用后要做什么；结论是"不采用"时，在对话中结束，不写文件。

## 0.2 判断是否需要头脑风暴

需求已经明确的迹象：给出了具体验收标准、指明了要沿用的现有模式、描述了确切的预期行为、范围受限且清晰。

需求已经明确时，保持简短：确认理解，给出简明的下一步选项，不强行展开长时间讨论。是否写文件仍按 0.3 的 Lightweight 规则判断。跳过 1.1 的扫描与侦察和整个 1.2，但仍要在 0.3 分级，然后直接进入 1.3 或 2.5，并严格按 `synthesis-summary.md` 的 Path A / Path B 规则处理——内容充分的开场属于 Standard 或 Deep，走 Path B（完整范围综述 + 确认），不能当作只需宣告。

## 0.3 判断规模

依据需求描述和一次轻量的仓库扫描分级：
* **Lightweight**：小、边界清楚、模糊度低；
* **Standard**：常规功能或有边界的重构，有一些决定要做；
* **Deep**：跨模块、战略性或高度模糊。

规模不清时问一个针对性问题再继续；仍不确定就取较重的一档。

**Lightweight 在对话中结束。** 结果是范围综述中的一段话：要做什么、做了哪一两个决定、它们接下来去哪（`nk-plan` 的输入或提交说明）。不写文件，不运行 1.1 侦察、第 2 阶段方案生成和 2.6 核实。只有对话产生了下游需要以稳定 ID 记录的决定，或用户要求时，才写文件；此时第 3 阶段依据对话中的决定写入，Ready for Planning Check 只核对对话已确立的内容。

**单一工作单元检查。** 进入第 1 阶段前，检查请求是否包含多个可以各自规划的产品成果：每个都有自己的用户价值或验收边界，可以不依赖其他部分单独交付。共享参与者、一个端到端成果、覆盖多个设备/服务商，本身都不构成拆分理由。发现多个时：
1. 用平实语言提出拆分，只写出现在能确定的关系：哪些依赖或促成其他部分、共享某条产品规则、可以独立推进；
2. 问用户本次头脑风暴负责哪一个（用户已选定则直接沿用）；
3. 只有选定部分产生需求、流程、验收示例以及后续的实施单元，其余部分只作为背景；
4. 保留对整体的当前理解，写入第 3 阶段的"How This Work Fits Together"一节，不确定的关系标为暂定；
5. 在 Goal Capsule 中点明当前部分，并说明其余部分不在本次范围内。

各成果无法单独产生价值或单独验证，或拆开会迫使本 Product Contract 编造缺失的共享行为时，保持为一个整体。本检查只收窄当前产物，不创建父 plan 或路线图。

**Deep 的两种子类型：**
* **Deep — feature**（默认）：已有产品形态作为决策依据，主要参与者、核心成果、定位和主要流程都已确立，本次在此形态内扩展或细化。
* **Deep — product**：本次要确立产品形态，主要参与者、核心成果、相对相邻产品的定位或主要端到端流程在实质上尚未确定。已有代码降低了这种可能，但不能排除——形态模糊的半成品工具仍属于这一类。它会在 1.2 触发额外问题，在 Product Contract 中增加额外章节。

**可视化触发条件。** 功能本质上是视觉或空间性的（绘图/画布、标注、可视化编辑器、界面布局或导航、交互状态、图表、动画、地图、时间线、空间流程）时，现在读取 `visual-probes.md`。读取只是准备；由该文件决定何时发出询问。

**陌生领域触发条件。** 用户表示缺乏该领域或相关代码区域的实际知识（"我对 X 一无所知""从没碰过鉴权模块""我不知道能做什么、该问什么"）时，现在读取 `blindspot-pass.md`。读取只是准备；由该文件决定何时提议。

## 0.4 任务清单

Standard 与 Deep 规模下，客户端有任务跟踪能力时使用它（按能力匹配，不按工具名）；Lightweight 和非软件路线不建。没有此能力就正常继续，不在对话里模拟清单。

主干是五项，按顺序：
1. 查看已有内容
2. 提出范围问题
3. 权衡方案并推荐
4. 写入前确认范围
5. 写入需求阶段 plan

条件性工作只在条件满足时才加入清单，插在实际运行的位置：例如已接受的盲区梳理、在后台运行的声明核实。每个决定都要跑一次的步骤不加，避免清单频繁变动。新加的任务照主干的命名方式：动词开头，五个字词左右，写用户能据以检查的结果，不写阶段名或内部动作。

条件变化导致某项不会运行时，记录为跳过，不要直接标记完成或悄悄消失：有 `cancelled`/`skipped` 状态就用；否则改名为"已跳过：<原因>"再标完成；实在不能改名才删除。无论哪种，都在对话中说明原因。

清单是给用户看的视图，不改变任何阶段的执行条件，也不能代替阶段自身的退出条件。
