# 范围综述（Synthesis Summary）

**综述 ≠ plan。** 综述不是需求阶段 plan 的预览、草稿或替代品，而是写入 plan 前的范围检查点，第 3 阶段以确认后的综述为输入写 Product Contract。综述与 Product Contract 都只写范围——实现细节（文件路径、代码结构、具体报错文案）属于 `nk-plan`。

**两段式。** 第一段是 Agent 内部的三栏草稿（已陈述 / 推断 / 范围外），用来全面思考范围；第二段是展示给用户的范围综述。用户只看到第二段。三栏草稿在第 3 阶段按本文件末尾的"确认后的文档结构"融入正文，本身不进入文档。这样分开，是因为全面审计式的呈现细节太多，用户无法真正参与判断。

所有规模都运行，包括 Lightweight；非软件路线跳过。本技能依赖对话；无人值守时按 `interaction-rules.md` 的"无人值守运行"处理。

---

## 第一段：内部三栏草稿

* **已陈述（Stated）**：用户直接说过的（原始请求、之前的对话、回答、第 2 阶段的方案选择），有用户原话为依据。
* **推断（Inferred）**：Agent 为补空缺做的假设——用户从未点明的范围边界、从意图推出的成功标准、简短访谈没问到而做的技术假设。用户的纠正在这一栏最有价值——这些是 Agent 的押注。
* **范围外（Out of scope）**：有意排除的内容——考虑过但决定不纳入的相邻工作、重构、锦上添花、未来工作。把排除项写明，才能发现其中其实应该纳入的。

一项同时属于两栏时（先纳入后排除），把它记为推断，保留推理过程。已定决策属于**带来源的已陈述**：连同类别、被否决的备选和一句理由记在已陈述栏，不放推断栏。

草稿是内部思考步骤，不要原样贴进对话。

---

## 第二段：对话中的范围综述

篇幅要能承接多轮对话，又只保留高影响的内容。参照：两个产品搭档讨论后互相说的话——"好，那我们做 X，接受 Y 这个取舍，Z 往后放，还有 W 我想再确认一下。对吗？"

最多四个小节，每节**有内容才出现**，空的省略，不凑数：

1. **要做什么**（总是出现）——1~3 句。对话中形成的形态，面向未来，平实用词。不是"你说了 X"的复述。
2. **关键取舍**（条件出现）——1~3 条，各附简短理由。只在对话中真的做过取舍时出现。
3. **不在范围内**（条件出现）——1~3 条，或合成一句。只在下游读者会对缺失感到意外时出现。
4. **提醒**（条件出现）——0~3 条。对话没解决的剩余分歧：多轮回答组合后才显现的后果、Agent 的隐性推断、或在无对话的预载场景中用户第一次看到的范围押注。**不是"1.3 本可以问却没问的问题"**——读起来像漏问的问题，说明 1.3 的整合检查失败了，应标出这个缺口而不是塞进本节。

已定决策写成 `Carrying forward:` 行，每条一行，放在"提醒"之前：`Carrying forward: <决定>，而非 <被否决的备选>——<一句理由>。` 它们是陈述，不是问题，也不是提醒项：确认针对整体形态，不针对用户已经做过的决定。

然后是确认，写明**接下来实际会发生什么**，让用户知道并能明确地打断：
* 预计写文件（常见情况）："确认后我就根据对话和这份综述写需求阶段 plan。或者告诉我要改什么。"
* 已确定不写文件（用户拒绝，或 `sections.md` 的"是否需要文件"标准明显成立）：写明这些决定实际的去处——本次对话确立的那个（`nk-plan` 的输入、提交说明、`docs/solutions/`）："确认后就到这里——上面的范围直接带入 [本次确立的去处]。或者告诉我要改什么。"对话没确立去处时删掉该从句："确认后就到这里——按你的要求不写文件。或者告诉我要改什么。"

不要写死去处。本阶段不写提交说明，也由第 3 阶段而不是本阶段决定是否写文件，所以不要在这里承诺不会发生的动作。

### Path A 与 Path B

由两个信号决定：(1) 2.5 之前是否问过阻塞式问题？(2) 0.3 的规模？阻塞式问题包括 0.3 的规模澄清、1.3 的对话追问、第 2 阶段的方案选择（展示了菜单时）。内部分类、1.1 扫描、1.2 压力测试不算。

* **Path A——没问过阻塞式问题，且规模为 Lightweight**：宣告并继续，不等待。只输出"要做什么"一段（没有其他小节，没有确认问题）。这段话就是结果；只有 0.3 的 Lightweight 规则认为需要文件时，才在同一轮进入第 3 阶段写入。不要停下等用户回应——形态不对时用户可以在结果出来后修改。
* **Path B——问过至少一个阻塞式问题，或规模为 Standard / Deep — feature / Deep — product**：完整的分档综述，之后必问确认。两种情形：用户在对话中投入了回答时间；或用户在开场预载了大量范围内容。两种情况都值得一个真正的检查点。即使没有任何提醒项，确认问题也照问。

**为什么要看规模。** 0.2 的快速通道面对两种截然不同的情况：一句话就够的紧凑请求（"修一下第 47 行的错别字"），以及因为用户预先说清了一切所以也不需要对话的大量预载内容（例如把之前会话积累的决定交过来补写文档）。只看"是否问过问题"会让后者也走 Path A，给可能 20 多项的范围只配一句话的检查点。不要把规则简化回单一信号——那是真实出现过的缺陷。

### 各小节的保留检验

**取舍：** 我不点明这个选择，用户会意外吗？真实的取舍是用户在对话中明确比较过备选的选择，或 Agent 做出的、用户会期待看到被点明的结构性选择。机械或必然的选择（"使用现有的规则实体"）不通过，只进文档正文。

**不在范围内：** 合理的下游读者会问"为什么 X 不在这里"吗？用户明确推迟的项，或相邻到读者会去找的项。机械性排除（"不做限流，因为不在范围内"）不通过，只留在内部草稿。

**提醒（可确认性检验）：** 用户需要读代码才能判断吗？需要，就是文档正文内容——删掉。不需要，则必须满足以下之一：
* **真实的范围分歧**——另一个合理的 Agent 可能在这个维度上选不同的范围（主要参与者是谁、情形 X 在内还是在外、做还是推迟）
* **不显而易见的纳入**——Agent 假设在范围内、用户可能想排除的行为
* **不显而易见的排除**——Agent 推迟了、用户可能想纳入的项
* **现在改便宜、以后改贵**——现在修正成本低、Product Contract 落地并被 `nk-plan` 使用后修正成本高的范围押注
* **多轮回答的非显而易见后果**——把用户的回答组合起来产生的、用户在对话中不太可能想到的下游影响。以面向未来的方式陈述（"X 意味着文档中 Y"），而不是回顾（"你说了 X"）。这正是头脑风暴需要提醒项的原因，不要以"已隐含在已陈述中"为由过滤掉

删除不符合上述任何一类的：已定决策；没有真实备选的机械项；规划阶段会确定的实现选择；综述正文已隐含的内容；对问答的复述；对用户已选方案的复述。

### 第 2~4 节的条目总预算

上限是经验值，真正的约束是每节对每个候选的保留检验。按规模的典型范围（取舍 + 不在范围内 + 提醒合计）：

| 规模 | 典型 | 硬上限 |
| :-- | :-- | :-- |
| Lightweight | 0~1 | 2 |
| Standard | 2~4 | 5 |
| Deep — feature | 3~5 | 7 |
| Deep — product | 4~7 | 9 |

**超过硬上限说明综述形状不对——不要提高上限，而是在更高的抽象层次重切。** 几乎总是同一节里多条其实是某个更大决定的子决定，合并成用户实际参与判断的那个层次的一条。检验方法：把条目读出来，两条以上听起来像"还有……"的延伸，就该合为一条。

Path B 中没有提醒项：Lightweight 常见，Standard 有时，Deep 几乎不会。Deep 综述内容丰富却没有提醒项时，检查是否把"后果类"提醒误当作"已隐含"过滤掉了。

### 详略：像对话，不像文档

每条**理想 1 行，最多 2 行**。综述是确认形态的手段，实质内容在 plan 里。一条写得像文档段落，就是形状错了——只做了横向压缩（条数少）没做纵向压缩（每条短）。两个检验：
* **读出来**：两个产品搭档会这样**说**，还是会这样**写**进规格？说——对；写——重切成一句或删掉。
* **一句话**：这条能用一句话说完吗？需要分号串联或条内列表，多半是两个决定挤在一条里——拆开（并重新检查数量）或只保留更高层的那个。

| 太细（错） | 对话式（对） |
| :-- | :-- |
| 按频道静音作用于通知规则；静音作用于该规则下所有事件，包括 @提及、转为通知的私信和机器人消息；持续 24 小时并可延长 | 按频道而不是按用户静音——支持团队不是一个人 |
| 删除规则会悄悄丢失暂停状态，可能让设置了长时间静音的用户意外；可以考虑确认对话框、保留状态的软删除或 7 天撤销期 | 删除规则会悄悄丢掉暂停状态——确认不需要提醒吗 |

"要做什么"同样遵守：1~3 句描述形态，不罗列需求。如果它列出了范围内外和实现方式，就成了文档预览——删到只剩形态。

### 反模式

* **任何条目中出现实现细节**：文件路径、模块名、具体 JSON 键、HTTP 状态码、报错文案、SQL。
* **原样复述问答**（"你说你想要 X"）：这是记录，不是综述。改成面向未来的写法（"X 意味着文档中 Y"）或删掉。
* **复述用户已选的方案**：它属于"要做什么"里的一句，不是提醒项。
* **为凑数填充小节**：空小节直接省略。
* **把三栏草稿原样贴进对话**：这正是第二段存在的原因。
* **综述旁边挂着悬而未决的问题**：某个问题确实无法用默认值处理时，暂停综述，先按合适的形式（选项有限且明显不同时用阻塞式选择，选项会左右回答时用开放式）解决它，把答案融入，再呈现综述。不要让综述旁边挂着没有明确解决路径的问题。

## 提问模板

确认问题用开放式（不用选项菜单）——菜单会把用户的反馈引向菜单列出的部分，远离他们可能想改的其他内容（提问规则第 6 条）。

"要做什么"的写法：面向未来（文档里**将会**有什么），不回顾讨论过什么；以实际要做的东西开头；不复述用户刚经历过的对话背景。无法不带填充词地用 1~3 句说清，说明综述还没准备好。

### Path B 模板

```
根据我们的讨论，我提议 Product Contract 的范围如下：

**要做什么：** [1~3 句——对话中形成的形态，面向未来，平实用词]

**关键取舍：** [有真实取舍时才写]
- [明确的选择 + 简短理由]

**不在范围内：** [推迟项会让读者意外时才写]
- [推迟项]

Carrying forward: [已定决策，每条一行]

**提醒：** [有通过保留检验的条目时才写]
- [用户可以确认或改向的范围分歧或非显而易见的后果]

[结尾——写明接下来实际发生什么，见上文"确认"。] 之前记对了的内容也可以改——你可能改了主意，或想纠正某个没说出口的假设。
```

### Path A 模板

```
提议：[1~3 行形态——平实地说要做什么]。

没有待定的决定——[需要文件时：现在写需求阶段 plan | 否则：这就是结果，这些决定进入 <本次确立的去处>]。形态不对请随时打断。
```

需要文件时，在同一轮进入第 3 阶段写入，不要停下等待确认；否则呈现第 4 阶段的交接。

### 示例：从内部草稿压缩到综述（Standard）

通知静音功能，内部草稿有 5 条已陈述、4 条推断、3 条范围外，压缩后：

```
根据我们的讨论，我提议 Product Contract 的范围如下：

**要做什么：** 在通知规则上按频道静音，提供 24 小时预设，解决支持团队凌晨 3 点被提醒的问题。静音挂在规则本身上，编辑规则后仍然保留。

**关键取舍：**
- 按频道而不是按用户——支持团队不是一个人
- 静音挂在规则上，而不是独立实体——编辑后暂停状态仍在

**不在范围内：**
- 基于在线状态的静音和免打扰时段——以后再做
- 跨规则的静音分组——会引入我们还没有的"规则分组"概念

**提醒：**
- 删除规则会悄悄丢掉暂停状态——确认不需要提醒吗

确认后我就根据对话和这份综述写需求阶段 plan。或者告诉我要改什么。
```

删掉的：已被"要做什么"覆盖的已陈述项；"使用现有规则实体"（机械，无真实取舍）；"用 Postgres 持久化"（实现细节）；"不做限流"（机械排除）；三条推断并入了取舍小节。

## 发出前复读

发出前以用户的眼光重读一遍，抓两种失误：
* **综述读起来像 Product Contract 预览**：正文罗列范围内外、条目像文档。改成对话式，或接受细节留给 plan、综述写轻一些。
* **条数符合上限，但每条都太细**：只做了横向压缩。重切成一句话的条目。

---

## 修改后重新呈现，确认后才写入

修改不等于确认。用户做了任何修改（即使只是"把 X 挪回范围内"这种一听就懂的改动），把改动融入，重新呈现修改后的综述，等明确确认后再写文档：
1. 呈现综述 → 用户回应
2. 用户确认 → 写文档
3. 用户修改 → 融入、重新呈现，回到第 1 步

只有明确确认，或在下文的阻塞式问题中选了"继续"，才写文档。

## 循环修改时的软中止（看是否绕圈，不看轮数）

记录每轮用户动过哪些条目。**只有同一条目被改了第二次**（或第三轮修改指向第二轮已改过的条目）时才问阻塞式问题。不同条目跨轮修改不设上限——逐个修正一份不对的综述，正是这个机制要支持的。

**跨轮是否"同一条目"按决定维度判断，不按措辞或所在小节。** 修改后综述可能重新推导——同一个决定可能换了说法、与别的条目合并、或换到别的小节。合并后的新条目继承其组成部分的"已改动"状态。

条件满足时，用阻塞式问题给两个选项：
* `继续并写入需求阶段 plan`
* `先别写——继续讨论`

## 用户改道

用户的回应表明用错了技能或想换一种流程（"这太小了，直接做吧"或"这需要更多思考，我换个方式"）时：停止头脑风暴；建议用户似乎想要的技能（例如 `nk-work`、`nk-plan`，或排查问题时的调试技能）；提议在本会话中加载；不争辩——用户的改道信号就是有意的选择。

## 确认后的文档结构

确认后，第 3 阶段写入需求阶段 plan。内部草稿不作为 `## Synthesis` 进入文档，只有"要做什么"一段作为 Summary 嵌入；其余内容融入 Product Contract 各节：

| 内部草稿 | 文档中的去处 |
| :-- | :-- |
| "要做什么" | Summary（1~3 行，面向未来） |
| 已陈述 | Requirements（带 R-ID，完整细节），需要叙述背景时也进入 Problem Frame |
| 推断 | Key Decisions（附理由）——用户在对话中接受的押注成为文档中的决定 |
| 范围外 | Scope Boundaries |
| 成功信号（已陈述或推断） | Success Criteria（当其适用时）——覆盖上面两行：成功信号只进这里，不同时进 Requirements 或 Key Decisions |

对话中的取舍小节融入 Key Decisions；"不在范围内"融入 Scope Boundaries。

已定决策是"已陈述 → Requirements"的例外：每条进入 Key Decisions 并带 `session-settled:` 标注——它是用户确认过的选择，不弱化为推断，也不记为假设。没有对话、直接依据上下文写文档时同样如此。

不写斜体的过程说明（"于 2.5 阶段形成……"）。Summary 与 Problem Frame 的分工见 `sections.md`。
