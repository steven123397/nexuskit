# 修复：工作区安全、测试先行与失败修复的含义 (Fix)

> **路径解析说明：** 本文件中引用的参考文件（如 `defense-in-depth.md`、`../../nk-work/`）均相对于本文件所在目录解析。

进入修复阶段、编辑任何文件前读本文件。**一次一个改动。如果你正在同时改多处，停下来。**

---

## 动手前

- **核对分支与工作区**：运行 `git status`。分支策略遵循项目约定（见 [`../../conventions/artifact-lifecycle.md`](../../conventions/artifact-lifecycle.md)），不自动建分支。修复需要触碰的文件若已携带用户未提交的改动，先与用户确认再编辑。
- **记录修复前现场**：当前 HEAD、`git status --short` 是否干净、既有改动文件清单。修复过程中维护**本次修复涉及的文件清单**——提交时只提交这些文件，不把无关改动带进提交。

## 测试先行序列

1. **选回归测试的归属**：从既有测试出发而非新建文件——既有失败测试已捕获缺陷就直接用；归属该契约但预期写错的更新它；因过度 Mock 而漏掉该缺陷的加强它；都没有合适的才新建一个最小独立测试（测试质量与 Mock 边界遵循 [`../../nk-work/references/testing.md`](../../nk-work/references/testing.md)）。测试必须在当前缺陷上失败、修复后通过；命名要让失败信息本身解释缺陷。若可达的接缝都无法以真实触发方式构造缺陷（缺陷需要接缝搭不出的调用链或状态），不要为虚假的安全感写浅测试——把缺失的接缝记录进调试总结，交给分层防御或复盘承接。
2. **确认测试因正确的理由失败**——是根因，不是无关的搭建问题。上一步因缺接缝未写测试时，复现回路就是本步与第 4 步的红绿仪表。
3. **实现最小修复**：只修根因，不顺手重构、格式化或清理无关代码——那些属于另外的提交。
4. **确认测试通过**；然后对**原始场景**（不只是最小化或测试形态的）重跑复现回路；再跑更广的测试套件防回归。原始场景无法在本环境重跑时，在总结与提交说明中如实注明"未验证"。
5. **自审 diff**：逐行读改动，检查风格、遗漏的边界、邻近行为的回归、缺失的覆盖。调试埋点必须全部清除——调查时给调试日志统一打过前缀标记的，一次 grep 即可确认清零。

## 修复失败意味着什么

修复没让复现转绿：回定位阶段，**明确作废当前假设**——陈述哪条证据证伪了它，再形成带自身支撑观察与预测的新假设。不要重试同一理论的变体（"也许是另一个分支""再补 catch 一种情况"），那是合理化螺旋，不是迭代。**3 次修复失败 = 触发智能升级**（见 [`investigate.md`](investigate.md) 的升级表）：根因定位很可能错了。

## 条件性分层防御

触发条件（满足其一即考虑）：

- 根因模式在 3 处以上文件出现（grep 修复签名验证）；
- 该缺陷在生产上本可以是灾难性的；
- 易受攻击的操作无论调用方是谁都危险（破坏性副作用、安全敏感、不可逆）。

满足则读 [`defense-in-depth.md`](defense-in-depth.md) 选择适用的层。一次性逻辑错误、没有现实复发路径的跳过。

## 条件性复盘

触发条件（满足其一）：缺陷上过生产；同一模式出现 3 处以上。分析它如何被引入、为何存活至今；发现的系统性缺口汇入收尾阶段的沉淀建议（`/nk-compound`）。
