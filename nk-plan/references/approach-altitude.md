# 做法层规划

阶段 0.1a 进入：不直接产出交付物，而是先产出"交付物将如何做出来"的做法 plan，停在检查点，再决定现在执行还是保存以后用。领域通用：交付物可以是文档、综合材料、学习资料，也可以是软件实施 plan。`nk-plan` 本身从不写代码、不运行代码。

## 1. 轻量侦察

做法 plan 的价值在于具体到可以评判。"读书、提炼主题、综合"这种通用方法论不值得批准。所以动笔前先浅读输入，只到能把做法落到具体内容为止，完整阅读留给执行：

* **按输入类型限定侦察量**：PDF 看章节标题、首末页和几个抽样章节；长录音稿看抽样片段和话题转折；代码库看入口和相关模块结构。找到重点和各部分关系就停。
* **落到具体**：说出做法要建立的具体联系（"录音稿有约 40 分钟在讲定价，对应书中第 3 章的框架，我会在那里把两者接起来"），而不是通用配方。
* **输入缺失时降级**：输入不在或稍后才到，就只从请求出发提出做法，并标明是临时的、未经侦察的；不要卡住等待，也不要用通用方法论充数。
* **不输出过程**：做法 plan 是给用户的价值，不是侦察日志。说结论，不说"我先看了 PDF，然后抽样了录音稿……"。

## 2. 撰写做法 plan（先在聊天中给出）

在聊天中给出，是否存档由用户决定。保持易扫读，按请求规模覆盖：

* **每个输入怎么处理**：从各自身上取什么，以侦察为依据。
* **怎么组合**：综合策略或顺序。这通常是风险最大、最值得确认的部分。
* **交付物的形态**：执行后会产出什么结构。
* **值得确认的分歧**：用户的倾向会实质改变结果的几个决定（例如某个来源权重更高、深度还是广度、面向谁）。
* **未决问题**：执行前用户应回答的问题。

这不是软件 plan 模板（没有实施单元和测试场景），除非交付物本身就是软件实施 plan——那种情况选"现在执行、代码"后进入正常的 `nk-plan` 流程。

## 3. 检查点

停在做法层。按 `../../conventions/decision-autonomy.md` 的提问规则提问；把正交的两个问题分开，第二个依赖第一个的答案：

1. 现在执行，还是保存以后用？
2. 仅在现在执行且领域不明显时：交付物是代码还是非代码？"保存以后用"时可以顺带提议深化这份做法 plan。

## 4. 分流

* **保存以后用**：存到 `docs/plans/`。非代码交付物在 frontmatter 写 `execution: knowledge-work`，让之后的 `nk-work` 走非代码路线。做法 plan 不写 `plan_contract: nk-plan/v1`，除非它同时具备完整软件实施 plan 的全部章节。正文保持与执行工具无关，任何 Agent 都能照着执行。
* **现在执行、代码交付物**：做法 plan 的任务完成，进入正常 `nk-plan` 流程（阶段 0.1b 起）产出实施 plan，然后交给 `nk-work`。
* **现在执行、非代码交付物**：在 frontmatter 写 `execution: knowledge-work`，把 plan 存到 `docs/plans/`（标记需要文件承载），然后交给 `nk-work`（它按 `../../nk-work/references/non-code.md` 执行）。无法调用时说明未开始执行，并给出一段可复制的交接说明：让下一个 Agent 用 `nk-work` 执行该 plan 路径。

## 与其他机制的区别

* **回答型任务的行动计划**（`universal-planning.md`）：不阻塞，说明做法后立即执行，产出聊天回答，只在非软件回答型分支。做法层规划领域通用、**停在检查点**、产出**可存档、可深化**的做法 plan。没有"先规划做法"措辞的调查型请求属于回答型任务。
* **范围确认**（0.7 / 5.1.5）：针对已决定要做的交付物，确认实施 plan 的范围。做法层规划决定的是要不要先承诺这个交付物。
* **深化**（5.3）：作用于已存在的 plan。做法层规划发生在任何产物存在之前。
