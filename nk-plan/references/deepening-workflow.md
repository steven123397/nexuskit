# 深化流程（5.3.3–5.3.7）

只在 5.3.2 判定需要深化时读取。

## 5.3.3 为置信度缺口打分

以清单为主、按风险加权。对每个章节计算：
* **命中数**：下面清单中适用的问题数；
* **风险加分**：话题高风险且该章节与风险实质相关，加 1；
* **关键章节加分**：Standard 或 Deep 中的 Key Technical Decisions、Implementation Units、System-Wide Impact、Risks & Dependencies、Open Questions，加 1。

候选章节：总分 2 分以上；或高风险领域中 1 分以上且章节重要。只选得分最高的 **2–5** 个章节；深化 Lightweight（高风险例外）时只选 **1–2** 个。plan 已有 `deepened:` 日期时，分数接近的情况下优先选还没被加强过的章节。

**各章节检查清单**

**Requirements**：需求含糊或与单元脱节；成功标准缺失或没在下游体现；单元没有清楚地推进所追溯的需求；上游需求没有明确延续；上游 A/F/AE ID 在规划决策涉及处没有保留，或在需求、单元、测试场景之间引用不一致。

**Context & Research / Sources**：提到了相关写法却从未用于决策或单元；引用的经验或参考没有实质影响 plan；高风险工作缺少内外部依据；调研泛泛而谈，没有落到本仓库或本 plan。

**Key Technical Decisions**：决策没写理由；理由没解释取舍或被否的备选；决策与范围、需求或上游没有关联；存在明显的设计岔路却没说明为什么选这条；Agent/工具/工作流类功能缺少关于操作对等、上下文对等、共享工作区、工具粒度或审批边界的明确决策。

**Open Questions**：产品阻塞被藏成假设；本应规划期解决的问题被推迟到实现；已解决的问题没有依据；推迟项太含糊，日后派不上用场。

**高层设计（存在时）**：形式不对；写成了实现代码而非伪代码；与关键技术决策或单元脱节。
**高层设计（缺失时，仅 Standard/Deep）**：工作涉及 DSL、API 接口设计、多组件集成、复杂数据流或状态密集的生命周期；关键技术决策用图示或伪代码更容易验证；单元的 Approach 单薄，需要更高层的设计提供背景。

**Implementation Units**：依赖顺序不清或可能错误；应写明的文件或测试路径缺失；单元过大、过于含糊或拆成了微步骤；Approach 单薄或没指出要参照的写法；测试场景含糊（没写输入和预期）、漏掉适用类别（有失败模式却没有错误路径、跨层却没有集成场景）、或与复杂度不相称；功能性单元测试场景空缺；验证结果含糊、不可观察；涉及 Agent 的单元缺少 Agent 原生验证（对等检查、上下文注入检查、工具结果检查、审批或失败行为、断点续做）；已有 U-ID 在调整顺序、拆分或删除后被改号；实现上游 Key Flow 的单元没引用 F-ID，落实上游验收示例的单元没引用 AE-ID。

**System-Wide Impact**：遗漏受影响的接口、回调、中间件、入口或对等面；失败传播考虑不足；相关时缺少状态生命周期、缓存或数据完整性风险；跨层工作的集成覆盖薄弱；功能影响 Agent 能力系统时，遗漏面向 Agent 的工具、提示词、运行时上下文、共享工作区、审批关卡或仅限人工的边界。

**Risks & Dependencies / Documentation / Operational Notes**：只列风险没有缓解措施；需要时缺少发布、监控、迁移或支持影响；外部依赖假设薄弱或未说明；明显适用的安全、隐私、性能或数据风险缺失。

以 plan 自身的调研和来源章节为证据：其中引用的写法、经验或风险如果从未影响决策、单元或验证，也算置信度缺口。

## 5.3.4 说明并派出定向调研

派出前先告诉用户要加强哪些章节、为什么：

```text
加强 [章节名] —— [每个的简短原因，例如"决策理由单薄""跨边界影响没理清"]
```

每个选中的章节选最小够用的子代理组合：**每章节 1–3 个，总数通常不超过 8 个**。下面的名字是 `agents/` 下提示词资产的文件名，读取后用其内容初始化通用子代理。

**章节 → 子代理对应**

* **Requirements / Open Questions 分类**：`spec-flow-analyzer`（遗漏的用户流程、边界情况、交接缺口）；`repo-research-analyst`（范围：`architecture, patterns`，核对仓库现实）。
* **Context & Research / Sources 缺口**：`learnings-researcher`（团队经验与已解决问题）；`framework-docs-researcher`（官方框架或库行为）；`best-practices-researcher`（当前外部实践）；`web-researcher`（格局或先例缺口、建议所依赖的尚未确定的外部选项）；历史缘由或先例确实缺失时加 `git-history-analyzer`。
* **Key Technical Decisions**：`architecture-strategist`（设计完整性、边界、架构取舍）；决策涉及 Agent、提示词、工具、MCP、工作流自动化、操作或上下文对等、共享工作区、审批关卡或 Agent 执行生命周期时加 `agent-native-planning-strategist`；需要仓库外依据时加 `framework-docs-researcher` 或 `best-practices-researcher`。
* **高层设计**：`architecture-strategist`（设计是否准确体现做法、有何缺口）；`repo-research-analyst`（范围：`architecture, patterns`）；涉及 Agent 编排、MCP/工具、提示词定义的行为、共享工作区、断点续做、审批或 Agent 与 UI 通信时加 `agent-native-planning-strategist`；涉及 DSL、API 接口或需要外部验证的写法时加 `best-practices-researcher`。
* **Implementation Units / Verification**：`repo-research-analyst`（范围：`patterns`，具体文件目标、参照写法、顺序线索）；`pattern-recognition-specialist`（一致性、重复风险、与现有写法对齐）；单元应覆盖 Agent 可访问的领域操作、工具或上下文变化、提示词变化或对等测试时加 `agent-native-planning-strategist`；顺序取决于用户流程或交接完整性时加 `spec-flow-analyzer`。
* **System-Wide Impact**：`architecture-strategist`（跨边界影响、接口面、架构连锁反应）；Agent 能力系统中加 `agent-native-planning-strategist`；再按风险加对应专家：`performance-oracle`（可扩展性、延迟、吞吐、资源）、`security-sentinel`（认证、校验、攻击面、安全边界）、`data-integrity-guardian`（迁移、持久化状态安全、一致性、数据生命周期）。
* **Risks & Dependencies / Operational Notes**：按实际风险选择：`security-sentinel`；`data-integrity-guardian`（迁移、回填、持久化数据安全、约束、事务边界、生产数据转换；这是规划语境，不是 PR 审查的 `data-migration-reviewer` 视角）；`deployment-verification-agent`（发布检查单、回滚计划、上线验证）；`performance-oracle`。

**给每个子代理传**：该 Agent 支持的范围前缀；plan 简要；该章节原文；为什么选中它（命中了哪些清单问题）；plan 深度与风险画像；一个具体要回答的问题。要求它返回：能改变规划质量的发现；更强的理由、顺序、验证、风险处理或参考；不写实现代码；不写 shell 命令。

## 5.3.5 选择执行方式

用最轻的可行方式：

* **直接模式**（默认）：选中的章节不多，主会话可以安全地直接读子代理的返回。
* **文件模式**：调研范围大到直接返回会造成不必要的上下文压力时才用。信号：可能有 5 个以上子代理返回实质发现；章节原文较长，在多个返回中重复会浪费；高风险话题可能引来大量带来源的分析。

文件模式在系统临时目录下新建本次运行专用的目录（如 `nk-plan-deepen-<随机串>`），记下绝对路径并传给每个子代理（传解析后的绝对路径，不传未展开的变量）。这些是一次性文件，深化结束后清理。

## 5.3.6 运行定向调研

并行派出选中的子代理；客户端不支持并行时依次进行。先用仓库和团队内部证据，只有在仓库上下文和已引用来源无法负责任地补上缺口时才做外部调研。某章节能靠更仔细地读上游文档来改善时，先读上游再派外部子代理。

* **直接模式**：子代理直接返回——只要最强的发现、关键证据或来源、它意味着的具体规划改进。
* **文件模式**：每个子代理在目录中写一个紧凑的文件（目标章节、选中原因、3–7 条发现、有来源的理由、每条发现意味着的具体改动；不写实现代码和 shell 命令），只返回简短的完成说明。文件缺失或明显损坏时重跑该子代理，或对该章节退回直接推理。

子代理结论冲突时：仓库证据和上游证据优先于泛泛的建议；关于库行为的冲突，官方文档优先于二手的最佳实践总结；仍存在真实取舍时，在 plan 中明确记录。

## 5.3.6b 交互式审阅发现（仅交互模式）

自动模式跳过，直接进入 5.3.7。

交互模式下，整合前逐个子代理展示发现：说明是哪个子代理审阅了哪个章节；简要列出关键发现、支撑证据和它意味着的 plan 改动；然后让用户选：**接受**（整合进 plan）、**拒绝**（全部丢弃）、**讨论**（先聊一下）。选"讨论"时简短讨论后再问一次，第二次只给接受或拒绝。

同一章节的多个子代理结果分别展示，让用户独立决定，不先合并。针对带 `session-settled:` 标注的 KTD 的发现照常展示（压制它们只是自动模式的行为）；用户接受了改变某个已标注 KTD 的发现，就是一次新的决定：更新 KTD 文字并改标为 `user-approved`。

全部审阅后只把接受的发现带入 5.3.7。一条都没接受时报告"没有接受任何发现——plan 未改动"，跳过自检和整合，直接进入收尾（`handoff.md`）。

## 5.3.7 整合并更新 plan

只加强选中的章节，保持 plan 连贯和整体结构。交互模式只整合用户接受的发现，多个子代理涉及同一章节时协调整合，不重新引入被拒的发现。

**已标注 KTD 的稳定性**：深化可以给带 `session-settled:` 标注的 KTD 补充理由或附冲突说明，但不能删除标注或反转决策。矛盾证据按严重程度处理：没发现问题 → 照常；可行但不理想 → 按已定执行并附冲突说明；不可行、做错东西或有破坏性 → 停下作为阻断项报告。

深化可以收紧，不只是增加：拆开多意图的句子、去掉含糊其辞、直接删除被取代的文字。更短且无矛盾的章节更强。

**在归属条目上加强**：规则在哪个 R 或 KTD 上写全，证据、理由和精度就加在那里；其他需要它的章节引用 ID。不要把已有归属的规则重述到 Key Decision、Scope 条目或单元 Approach 中；删除被加强章节里没有链接的平行重述本身就是有效的收紧。

**允许的改动**：按 `structure.md` 4.2 收紧被加强章节的文字（就地删除被取代的内容，把没有链接的重述改成对 R/KTD 的引用）；补强决策理由；收紧需求追溯或对上游的忠实度；顺序薄弱时调整或拆分单元（**绝不改动已有 U-ID**）；补上参照写法、文件或测试路径、验证结果；在有依据时扩展系统级影响、风险或发布处理；有证据时在"规划期已解决"与"推迟到实现"之间重新归类问题；在需要时加强、替换或新增高层设计；在做法不明显的单元加强或新增技术设计字段；plan 被实质改进时在 frontmatter 添加或更新 `deepened: YYYY-MM-DD`。

**不要**：加实现代码（伪代码和 DSL 草图可以）；加 git 命令、提交编排或测试命令配方；到处加泛泛的"调研心得"小节；从头重写整份 plan；在没有明说的情况下发明新的产品需求、范围变化或成功标准；为了"整洁"而重新编号 U-ID（深化是最容易误改号的环节）；删除或改写 `topic:` 字段与 `<!-- nk-section: ... -->` 语义标记；把 R 或 KTD 已拥有的规则重述到兄弟章节。

调研揭示了会改变行为或范围的产品层模糊点时：不在这里悄悄决定，记入 Open Questions；确实是定义产品的缺口时建议 `nk-brainstorm`。

整合后进入写后自检（`self-review.md`）。
