# 收尾与交接（5.4）

写后自检完成后读本文件。Direct、Chat brief、非软件规划和做法 plan 各有自己的结束方式，不走这里。

## 能否交给实施

对照 plan 的实施章节和仓库证据评估最终 plan：仍有未核实的实质前置条件、或仍有妨碍开工的问题时，**不提供实施选项**，在 plan 和交接中写明阻断项。推迟的细节和计划中新建的文件不妨碍交接。

**请求已授权下一步**（例如"规划完直接开始做""规划好就停"）时，直接执行那一步，不再出菜单询问。

## 菜单上方的一行

先用一行报告自检结果，例如：`自检修正了 3 处，还有 1 个需要你决定的事项、2 条观察。` 没有修正也没有遗留时：`自检通过，无需修改。` 然后只展示仍需用户处理的事项：每条写建议、不改的后果、要改什么、依据。已放下或已完成的事项不再出现。

## 菜单

问题：`Plan 已就绪：<plan 的绝对路径>。接下来做什么？`

按 `../../conventions/decision-autonomy.md` 的提问方式给出（客户端的选择题工具放不下时，改为聊天中的编号列表并提示"选一个编号或直接说你想做什么"）：

1. **开始实施：结束本会话，由新会话接手** *(Recommended)*——读取 `../../nk-handoff/SKILL.md` 并照做：覆盖更新 `docs/current.md`，"下一步"写成本 plan 的第一个可开工单元（如"`<plan 路径>` 的 U1"）；把本会话的规划产出（本 plan、`CONCEPTS.md` 的改动、`docs/current.md`）合成**一次**交接提交。新会话用 `nk-work` 从 `docs/current.md` 接手。只在 plan 支持实施且没有阻断项时显示。
2. **在本会话直接开始实施**——读取 `../../nk-work/SKILL.md`，以本 plan 路径和第一个单元为输入开始。此时**不单独提交**规划产出：它们留在工作区，随第一个单元的提交一起入库（`../../conventions/commit-cadence.md` R4 第 2 条）。显示条件同上。适合 plan 较小、当前上下文仍宽裕时。
3. **处理自检遗留的决定**——逐条展示需要用户决定的事项，按用户选择修改 plan，然后重新展示本菜单。仅当自检留下了需要用户决定的事项时显示。
4. **继续深化**——进入 `deepening-workflow.md` 的交互模式，完成后回到自检和本菜单。
5. **拆成 Issue**——用 `nk-to-tasks` 把单元拆成 Issue（适合需要并行或长期挂起的 plan）。`nk-to-tasks` 尚不可用时不显示此项。

没有"完成"选项：用户不选或直接结束对话即可，plan 文件已经保存。用户选择了"开始实施"之外的路线又要结束会话时，提醒按选项 1 的方式做一次交接，以免规划产出只留在工作区。

## 执行所选项

用户在后续回合做出选择时，先重读本文件再执行。展示菜单、收到选择或宣布路线都不算完成，要真正执行所选动作：

* **结束本会话交接**：按 `nk-handoff` 完成更新与提交，报告提交哈希和"下一步"。
* **本会话直接实施**：先确认 plan 支持代码实施且无阻断；需求阶段的 plan 回到本技能补全，非代码 plan 交给其非代码路线。然后按 `nk-work` 开始。无法按 `nk-work` 执行时，给出一段可复制的说明：让下一个执行者用 `nk-work` 执行该 plan，先按标题定位 Goal Capsule、Verification Contract、Definition of Done 和当前 U-ID，而不是先通读全文。
* **处理遗留决定**：逐条确认后修改 plan，重跑 `structure.md` 4.2 的检验，重新展示菜单（更新计数）。
* **继续深化**：见 `deepening-workflow.md`。
* **拆成 Issue**：按 `nk-to-tasks` 执行，完成后展示 Issue 链接，再询问是否开始实施。

**其他自由输入**：用户直接提出修改意见时，接受修改、改进 plan，然后回到本菜单。

## 临时目录清理

调研或深化用过临时目录时，plan 安全写入后清理；平台上不便清理时说明文件留在了哪里。
