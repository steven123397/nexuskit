# 阶段 0：续写、分流与定界

进入 `nk-plan` 后第一个读的文件。依次完成 0.1–0.7；某一步选定了其他路线就照那条路线走，不再继续往下。

---

## 核心原则（贯穿全程）

1. **Product Contract 是事实来源**：已有 `nk-brainstorm` 产出的需求阶段 plan 时，就地补全同一文件，不重新发明产品行为，也不另起第二个文件。
2. **写决策，不写代码**：记录做法、边界、文件、依赖、风险和测试场景。不预写实现代码、不写 shell 命令编排。高层设计可以用伪代码或 DSL 草图传达方向，但要注明是方向性示意。
3. **先调研再成形**：定稿前先看代码库、`docs/solutions/` 和必要的外部资料。
4. **按规模定篇幅**：小工作写紧凑的 plan，大工作写更多结构，方法论不变。
5. **规划期问题与执行期发现分开**：能在规划时回答的现在回答；取决于写代码后才知道的，明确推迟到实现时。
6. **plan 可移植**：它应能作为活文档、评审材料或 Issue 正文使用，不嵌入某个执行工具专用的指令。
7. **执行方向轻量携带**：请求、上游文档或代码现状明显要求测试先行、先做特征测试、以冒烟验证为主等非默认方向时，在相关单元里用一句自然语言写明，不做成枚举，也不写成逐步编排。
8. **尊重用户点名的资源**：用户指名的 CLI、文件、链接、先前产物是权威输入。不认识就先去发现（`command -v`、读取、抓取）；确实不可用就明说，不悄悄换成别的。

**质量底线**：清楚的问题背景与范围边界；需求可追溯到请求或上游文档；仓库相对路径；功能性单元写明测试文件路径；决策带理由；指出要遵循的现有写法；每个功能性单元列出具体测试场景；依赖与顺序清楚。关于现有代码和夹具的实质性说法要对照仓库核实；妨碍实施的前置条件未满足时记为阻断项。计划中新建的东西不需要已存在。

---

## 0.1 续写已有 plan

用户点名了已有 plan，或 `docs/plans/` 中有明显匹配的近期 plan 时：

* 读取它，确认是就地更新还是新建。更新时只改仍然相关的章节。plan 不记执行进度（进度以带 U-ID 的提交为准），没有进度需要保留。
* **只有 Goal Capsule 与 Product Contract 的需求阶段 plan 不是续写对象**，而是补全输入：不询问"更新还是新建"，直接进入 0.2 就地补全。
* **深化意图**：用户说"深化这个 plan""再深挖一轮"等明确针对整份 plan 的请求时，进入深化快速通道。"加强""补充""缺口"这类词本身不算，只有明确针对整份 plan、又没点名具体章节时才算，拿不准先确认。
  * 目标 plan 看起来完整（主要章节齐全、单元已定义）且带 frontmatter：直接跳到最终审查与深化（`final-review.md` 的 5.3），用**交互模式**。
  * 没有 frontmatter 的 Markdown（非软件 plan 用 `# 标题` 加 `Created:` 日期）：改走 `universal-planning.md`。
  * 已有 `deepened:` 日期且用户没要求重新深化：照样做置信度评估，但不强制深化。
* 普通编辑请求（"补一个单元""更新测试场景"）走普通续写，不走深化通道。

## 0.1a 识别"先规划做法"的请求

用户明确要求"先规划怎么做""plan 一下做法，先别动手"时，进入做法层规划：读 `approach-altitude.md` 并按它执行。

主动提议做法层规划要很克制：只有**方法本身不确定**（几种方法会产出不同的交付物，或多个来源怎么结合不清楚）**且**做错代价高时，才用一句可忽略的话提议。规模大但方法显而易见的工作（大批量迁移、全局改名）不提议。拿不准就不提。

## 0.1b 区分软件与非软件任务

构建、修改、重构、部署软件（代码、数据结构、基础设施）是软件任务，继续 0.2。按任务类型分，不按话题分：只是"涉及"代码库的调查或分析属于回答型任务。领域确实模糊时先问用户。

否则读 `universal-planning.md`，按它的流程走，跳过后续所有软件阶段。

## 0.2 查找上游 Product Contract

按顺序查找：

1. **用户给出的路径**：读取。只有 Product Contract 的 plan → 本次就地补全；已有实施部分 → 当作续写或深化目标。`docs/current.md` 的"下一步"写着"用 nk-plan 规划 <plan 路径>"（`nk-brainstorm` 交接的写法）时，也按给出路径处理。
2. **近期待规划的 Product Contract**：在 `docs/plans/*.md` 中找 `product_contract_source: nk-brainstorm` 且尚无实施部分的 plan，看内容判断。
3. **历史需求文档**：其他形式的需求文档（如旧体系留下的 `*-requirements.md`）可作为 `origin` 读取，不迁移、不改写。

**相关性**：frontmatter 的 `topic:`（`nk-brainstorm` 写入的可选字段）与本次需求一致时优先视为同一需求；否则看主题语义匹配、30 天以内（明显仍相关或明显过时时自行判断）、覆盖同一个用户问题。多个都匹配时让用户选一个。

**本会话已定的决策**是与文档并列的输入层：对话中经过权衡后由用户拍板的决策，作为已定约束进入规划，不是待决问题。分类前读 [`../../conventions/settled-decisions.md`](../../conventions/settled-decisions.md)。

## 0.3 以 Product Contract 为主要输入

存在需求阶段 plan 时：

1. 读 frontmatter、Goal Capsule、Product Contract、Open Questions、Sources（按标题定位，不读长附录）。
2. 告诉用户本次会在同一文件中补上实施规划。
3. **保留 Product Contract 的含义和稳定 ID（R/A/F/AE）**，除非规划发现直接冲突；冲突写成明确的假设或问题，不悄悄改产品范围。
   * 保留的是决策，不是字节。不改变含义的重组是允许的：拆分过载的需求（原 ID 保留原核心意图，拆出部分取下一个未用编号）、把规则的完整表述移到管辖它的 R 上、删除没有链接的重复表述。拆分或移动后，所有 `Governs R…`、`Covers R…`、行内 `per R…` 引用都要改指向新的 ID。重组不能削弱限定条件、丢掉边界情况、或把产品约束降格成实现偏好——那是范围变化。
   * 补全后的 plan 里写一行 **Product Contract 保留说明**："Product Contract 未改动"，或"重组、范围不变：<旧 ID → 新 ID>"，或"已改动：<R-ID> —— <原因>"。**实质性的产品范围变化**要先和用户确认，再写实施单元。
4. 延续所有适用的 Product Contract 章节，作为规划与调研的主要输入。
5. 不另建重复的 plan。保留上游写入的 `topic:` 字段和 `<!-- nk-section: ... -->` 语义标记（如 `<!-- nk-section: work-relationships -->`）：它们供下游技能识别，就地补全时原样保留、不改写、不删除。

存在历史需求文档时：通读；说明它作为本次规划的上游；延续问题背景、参与者/流程/验收示例（保留 ID，作为单元必须遵守的约束）、需求与成功标准、范围边界、关键决策及理由、依赖与假设、未决问题（保留"阻塞/推迟"区分）；在 frontmatter 写 `origin:`，在 plan 中引用重要决策时注明 `(see origin: <路径>)`；定稿前逐节核对没有遗漏。

没有任何上游时，直接从请求出发，写出完整 plan，`product_contract_source: nk-plan`。

**已定决策与上游产品决策同等保护**：调研只能补充，不重问、不悄悄改写。发现矛盾证据时按严重程度处理：没发现问题 → 照常；可行但不理想 → 按已定执行，并在对应条目上附冲突说明；导致不可行、做错东西或有破坏性 → 停下，作为阻断项报告给用户。

## 0.4 没有需求文档或输入不清时的规划引导

* 先判断请求是否已足够清楚：问题背景、范围边界、成功信号已知或可记为假设 → 直接进入 0.5。
* 模糊点主要在产品层面（用户行为、范围定义）→ 建议 `nk-brainstorm`，同时提供在这里继续的选项。
* 用户表示不熟悉这个问题领域 → 建议 `nk-brainstorm`，尊重用户选择；在这里继续时，阶段 2 的提问改用"教学式"（见 `structure.md`）。
* 继续在这里时，简短建立：问题背景、预期行为、范围边界与明显的非目标、成功标准、阻塞问题或假设。

**退出条件**（或用户明确要求继续）：问题背景已**明确陈述**；重要的范围内外边界已知；成功标准已知或记为假设。边界和成功信号可以用假设满足，问题背景不能——它是必填章节，假设出来的背景会把未经验证的猜测变成产品范围。请求只给了做法没给目标时，从请求自身的动机推出目标（做法成为 Goal Capsule 的 Means，而不是 Objective），推不出就问。

引导中发现重大的产品问题 → 再次建议 `nk-brainstorm`；用户仍要继续就要求写明假设。

**缺陷型请求**（"修一下 X 的 bug"、报错、回归）：代码可达时，提供改用调试流程的选项（NexusKit 的 `nk-debug`；尚未提供时用可用的调试方式），与继续规划并列。代码在另一个本地路径时，先说明要读哪个仓库、plan 写到哪里（默认写到目标仓库的 `docs/plans/`），再继续。无人值守时不提供这个选项，按用户的显式调用继续规划。

## 0.5 规划前先处理未决问题

上游文档中有"规划前需解决"之类的阻塞问题时逐条审视：确属技术、架构或调研问题的，转为规划期工作；会改变产品行为、范围或成功标准的，保留为阻塞。

仍有真正的产品阻塞时，说明清楚，并让用户选：回到 `nk-brainstorm` 解决，或把它们转为明确的假设或决定后继续。阻塞未解决前不继续规划。

## 0.6 选择输出档位与规划深度

基于请求点名内容的有限阅读（不派子代理）选择**输出档位**：

* **Direct**：一次就能说清、做完、验证，没有需要用户权衡的决策。
* **Chat brief**：范围有限，至多一个需要用户权衡的决策，没有风险面。
* **Durable**：其余情况。

选 Direct 或 Chat brief 时读 `output-contracts.md` 并按它结束。拿不准时取更重的一档；阅读中发现需要用户权衡的决策、风险面或需要多轮验证，立即升档。以下情况一律 Durable：无人值守运行；请求明确要一个 plan、plan 文件或某种格式；请求是续做已有 plan 的某一项；涉及风险面（认证、支付、迁移、对外契约）。

Durable 再分**规划深度**：

* **Lightweight**：小、边界清楚、模糊性低。
* **Standard**：常规功能或有边界的重构，有一些技术决策需要记录。
* **Deep**：跨领域、战略性、高风险或高度模糊的实施工作。

深度不清时问一个针对性问题再继续。宿主有任务跟踪能力时，用它展示路线级进展；没有就照常进行，不在聊天里模拟。

## 0.7 独立规划时的范围确认

**仅在以下条件同时满足时运行**：0.2 没找到上游 Product Contract；0.4 留在 `nk-plan`；0.5 无阻塞；不在 0.1 的续写或深化通道上；0.6 选了 Durable。有上游来源的规划改在写 plan 前做确认（`final-review.md` 的 5.1.5）。

目的：在派出调研子代理这个昂贵步骤之前，让用户纠正范围。**先读 `synthesis-summary.md`**，按它构造"独立规划"变体：内部三分草稿（明确说的 / 推断的 / 范围外）→ 提炼真正的分歧点 → 按模板展示并**等待确认**再进入调研。

* 只有 **Lightweight 且没有任何分歧点**时，才可以只发一行说明直接继续。
* Standard 与 Deep 即使没有分歧点也要等确认。
* 用户说过"直接写，不用确认"，或无人值守时：不等待，推断项在写 plan 时放进 `### Assumptions`。这只跳过这一次范围确认，其余阻塞问题和收尾菜单照常。
