# 范围确认（Scoping Synthesis）

**范围确认不是 plan 本身。** 它是一个"范围与决策"检查点，写 plan（5.2）时以它为输入。它只展示此刻能做出的决定：范围层面（覆盖全部上游范围，还是只做一部分？）、做法层面（沿用现有模式还是引入新抽象）、测试范围。它**不**展示写 plan 时才产出的东西：PR 数量、提交或分支顺序、工作量估计、实施单元列表、具体文件路径、测试命令。出现这些就说明混进了写 plan 的内容，要重新裁剪到范围层面。

## 两种变体

* **独立规划变体**（阶段 0.7）：没有上游 Product Contract。在调研之前运行，避免子代理在错误的范围上花力气。覆盖面最广：问题背景、预期行为、成功标准、范围内外。
* **承接上游变体**（5.1.5）：有上游 Product Contract。在调研之后、写 plan 之前运行，只关注规划期决定（动哪些模块、沿用还是新建模式、测试范围、顺带重构的去留）。上游已确认的"做什么"视为已知，不再复述。

## 两个阶段：内部草稿 → 聊天中的确认

**第 1 阶段：内部三分草稿**（不直接贴给用户）

* **明确说的**：用户在请求、对话、问答或上游文档中直接说过的内容。
* **推断的**：Agent 为补空白做的假设——用户没点明的范围边界、从意图外推的成功标准、没问到的技术假设。这是最值得用户纠正的一栏。
* **范围外**：刻意排除的内容——考虑过但不纳入的相邻工作、重构、锦上添花、未来工作。

本会话已定的决策属于"明确说的"并带来源，永远不是"推断的"。

**第 2 阶段：聊天中给用户看的确认**：按规划深度控制篇幅的摘要，加若干"分歧点"——用户可能想改方向的具体岔路。

## 篇幅上限（是上限不是目标）

| 深度 | 上游范围复述（承接变体） | 规划期范围决定（承接变体）/ 范围声明（独立变体） |
| :-- | :-- | :-- |
| Lightweight | 1 句 | 1–3 行 |
| Standard | 1–2 句 | 3–5 行或 2–4 条 |
| Deep | 1–2 句 | 4–6 行或 3–6 条 |

## 共同规则

* 聊天中不单列"明确说的"和"范围外"。非显而易见的排除项如果通过保留测试，就作为分歧点出现，否则省略。
* 已定决策显示为 `延续：` 行（一行一条：决策、类别、否掉了什么），放在分歧点之前，不作为分歧点。
* 用上游文档的术语，不自造 Agent 内部缩写。提到需求、流程、验收示例时用平实名称，**不写裸 ID**（`R3`、`AE2`、`U1` 等）。
* **发出前自检**：扫描裸 ID 和文件路径，除非路径本身就是某个分歧点讨论的对象，否则删掉。

## 分歧点的保留测试

先做**可确认性测试**：用户需要看代码才能判断吗？需要 → 这是 plan 正文内容，删掉。不需要 → 至少满足下面一条才保留：

* **真正的岔路**：另一个合理的 Agent 可能选不同的做法。
* **不明显的行为选择**：只读摘要看不出、但实质影响 plan 行为的默认选择。
* **不明显的排除**：刻意排除、用户可能想加回来的内容。
* **现在改便宜、以后改昂贵**：用户此刻纠正代价很低，写完 plan 后再改代价高的赌注。

删掉：没有真正替代方案的机械性选择；实现时自然会定下的细节；摘要里已经隐含的内容。

**细节测试**：每个分歧点 1–2 行，口语化。一个分歧点写到 4 行以上的密集文字，说明它在描述实现后果而不是决定，要提高抽象层次重写。

## 分歧点数量

| 深度 | 常见 | 上限 |
| :-- | :-- | :-- |
| Lightweight | 0–2 | 3 |
| Standard | 1–3 | 4 |
| Deep | 2–5 | 6 |

超过上限，或有分歧点写得过长，都说明拆得太碎：几个分歧点往往是同一个大决定的不同侧面（文件位置、参数名、数据键、依赖选择常常只是"如何扩展现有结构"一个决定），合并成用户真正会表态的那一层。

**不要写进分歧点**：文件路径或模块名、参数名或环境变量值、JSON 结构或返回格式、HTTP 状态码或事件名或错误文案、实现流程（"先 X 再 Y"）、方法签名或 SQL、没有替代方案的机械选择。

## 何时可以不等确认

* **Lightweight 且没有任何分歧点**：发一行说明后直接继续：

  ```
  规划：[1–3 行范围说明]

  没有需要你表态的决定，直接进入[调研 / 写 plan]。如果范围理解错了请打断我。
  ```
* **Standard 与 Deep**：即使没有分歧点也要等确认（省略"分歧点"标题即可）。
* **用户说过不用确认**：任何深度都不等待，但仍要发说明：

  ```
  规划：[1–3 行范围说明]

  已按你的要求跳过范围确认，直接进入[调研 / 写 plan]。推断的范围记在 plan 的 Assumptions 中，如有不对请打断我。
  ```
* **无人值守**：不发确认，也不发说明；内部草稿直接按下文"写入 plan 的去向"处理，推断项进 `### Assumptions`。

## 模板

**独立变体（阶段 0.7）**：开头默认"根据你的请求"；只有 0.4 中确实来回问答过，才加"以及我们的简短讨论"。

```
根据你的请求，我打算按以下范围规划：

[范围声明：规划覆盖什么、不覆盖什么；可确认层面；不列实施单元]

**延续：**（没有已定决策时省略）
- [决策 —— 类别；否掉了 <备选>]

**分歧点：**（没有时省略）
- [决定层面的岔路，1–2 行；可附一句取舍说明；不写长篇理由，理由写进 plan 的关键技术决策]

确认后我开始调研。（如果这比你预想的大，也可以改用 `nk-brainstorm`，我会在这里停下。）
```

**承接变体（5.1.5）**：

```
上游需求的范围是 [1–2 句复述，用上游文档的原词；不列单元、约束或验收示例]。

本 plan [规划期的范围决定：相对上游覆盖了什么、推迟了什么、扩展了什么；测试范围；相邻重构纳入还是排除]。

**延续：**（没有已定决策时省略）
- [决策 —— 类别；否掉了 <备选>]

**分歧点：**（没有时省略）
- [规划期岔路，1–2 行]

确认后我开始写 plan。
```

## 修订不等于确认

用户做了任何修改（哪怕很小），都要整合修改、重新展示修订后的确认、再等待明确确认，然后才写 plan。

**循环止损**：同一个分歧点（按决定本身识别，不按措辞）被第二次修改时，问用户："继续，进入[调研 / 写 plan]"还是"先停一下，继续讨论"。新的分歧点不受此限。

## 用户想换技能

独立变体中用户说"这比我想的大，先 brainstorm"→ 建议 `nk-brainstorm`；"只是个修复，不用 plan"→ 建议 `nk-work`；"我得先查一下"→ 建议调试流程（`nk-debug`）。承接变体中用户说"上游范围不对"→ 建议回到 `nk-brainstorm` 修改。无论哪种：停下 `nk-plan`，提议加载对应技能，不争辩。

## 写入 plan 的去向

确认后（或止损问题选择继续后），内部草稿按下表融入 plan，不单设 `## Synthesis` 章节，只有第 2 阶段的摘要写进 Product Contract 的 `### Summary`：

| 草稿内容 | 写入位置 |
| :-- | :-- |
| 第 2 阶段摘要 | Product Contract `### Summary`（1–3 行，前瞻性）。独立变体：规划的范围；承接变体：实施做法 |
| 明确说的 | Product Contract `### Requirements`（R-ID），需要时写进 `### Problem Frame` 作为背景 |
| 推断的 | Planning Contract 的关键技术决策（带理由），驱动结构选择时体现在实施单元中。无人值守或跳过确认时改放 Planning Contract `### Assumptions`，明确标为未经验证的 Agent 假设 |
| 范围外 | Product Contract `### Scope Boundaries`，需要时含 `#### Deferred to Follow-Up Work` |
| 成功信号 | Product Contract `### Success Criteria`（替代而非叠加上面两行）。明确说的总是写入；推断的只在交互确认过的情况下写入，否则放 `### Assumptions` |
| 已定的产品决策 | Product Contract `### Key Decisions`，带 `session-settled:` 标注和 `Governs R…` 链接；已定的技术决策进关键技术决策 |

在交互确认过的 plan 中，两类推断内容即使没通过分歧点保留测试也要写入：从意图外推的成功标准（进 `### Success Criteria`）和用户没点明的范围边界（进 `### Scope Boundaries`）。保留测试决定问不问用户，不决定产品范围是否写进文档。

Summary 与 Problem Frame 分工不同：Summary 回答"这个 plan 提议做什么"（前瞻，1–3 行）；Problem Frame 回答"为什么要做"（回顾，段落）。互不重复。

## 不属于范围确认的内容

实现代码；整份上游文档的复述；防御性的假设和含糊其辞；原样贴出的三分草稿；游离在分歧点之外的问题。确实无法默认的问题要在展示确认之前先解决：选项有限且有明显差异时用选择题，选项会诱导答案时用开放提问；拿到答案后再展示确认。
