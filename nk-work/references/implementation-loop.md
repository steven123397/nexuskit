# 实施循环与证据策略 (Implementation Loop)

本文件规范 `/nk-work` 中实施单元的标准推进循环、测试发现与系统级验证检查。

---

## 一、已完成检查 (Already-Done Check)

在动手编写代码或测试前，先进行快速核查：
* 当前代码库中是否已经实现了本单元所要求的功能？
* 该功能是否已满足本单元约定的所有验证标准？
* **若已完成**：在终端运行对应测试加以验证。通过后直接标记本单元已完成，向用户报告核实结论，避免在跨会话接力或重叠开发中重复劳动。

---

## 二、风格对齐与测试发现 (Discovery)

1. **参照既有代码**：在编写新代码前，检索同模块或临近模块的现有实现，对齐命名习惯、错误处理模式（如 `Result`、异常类）、日志与异步规范。
2. **测试发现 (Test Discovery)**：
   * 明确仓库现有的测试框架（如 `pytest`、`vitest`、`cargo test`、`go test`）；
   * 找到**最快速的单文件/单用例运行命令**（如 `cargo test parser::test_stream` 或 `npm test -- path/to/spec.ts`），将反馈循环压制在数秒内；
   * 明确全套测试的执行方式，留待最终收尾时运行。

---

## 三、证据策略表 (Evidence Strategy)

根据改动性质，选定对应的验证证据策略：

| 改动类型 | 核心验证要求 | 证据产出物 |
| :-- | :-- | :-- |
| **纯逻辑 / 算法** | 单元测试全覆盖，包含正向与边界测试 | 测试运行日志及 100% 通过输出 |
| **跨模块 / 集成交互** | 集成测试或端到端模拟用例，验证契约闭环 | 集成测试命令输出、时序/返回体断言结果 |
| **前端 / UI 交互** | 见 `references/ui-work.md`，走查响应式布局与交互 | 模拟渲染输出、无报错控制台日志、交互走查结论 |
| **依赖外部系统状态** | 见 `references/out-of-repo-state.md`，验证外部服务契约 | 模拟存根（Mock）测试 + 实际调用证据（若连通） |
| **文档 / 配置类** | 见 `references/non-code.md`，验证配置解析与有效性 | 校验脚本退出码、语法检查通过证据 |

---

## 四、测试推进节奏 (Testing Cadence)

结合 Matt Pocock 与 CE 的实战测试节奏：
1. **单切片聚焦**：不要一次性为整个复杂系统写完所有测试再开始实现；每次只专注于一个切片（Seam）的一个测试用例。
2. **红绿循环**：
   * **Red**：先写出失败的测试用例，运行并确认其由于目标逻辑缺失而准确变红（退出码非 0）；
   * **Green**：编写最少量的实现代码，重新运行该测试用例，确认变绿（通过）；
   * **Refactor**：在测试保护下局部优化代码，保持测试常绿。
3. **分层执行节奏**：
   * 循环中途：仅频繁运行当前单个测试文件和轻量类型检查（编译检查）；
   * 单元完成前：运行关联模块测试套件，最后运行受影响的全量测试。

---

## 五、系统级收尾自检 5 问 (System-Wide 5 Checks)

在声明实施单元完成并调用 `/nk-commit` 提交前，逐一确认以下 5 个问题：

1. **测试是否实际运行？** 是否有终端实际命令和通过证据？未运行的测试必须明确标记为“未验证”。
2. **是否破坏相关联的现有功能？** 是否运行了关联模块的已有测试套件，确认无意外回归？
3. **是否存在类型或静态分析警告？** 是否执行了 Lint 或编译器类型检查，无新增告警？
4. **是否存在向后兼容性破坏？** 公开接口、数据 Schema 是否符合 `conventions/decision-autonomy.md` 约束？
5. **工作区是否纯净？** 是否清理了所有调试打印（`console.log`、`dbg!`、`print`）和临时测试文件？
