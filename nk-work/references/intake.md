# 任务输入与范围判定 (Intake)

本文件规范 `/nk-work` 如何解析输入、分流处理直接需求以及按需阅读 Plan 文档。

---

## 一、输入类型与解析

| 输入类型 | 判定特征 | 解析动作 |
| :-- | :-- | :-- |
| **Plan 单元** | 携带 U-ID（如 `U2`）或 Plan 文件路径加单元号 | 定位 Plan 文件，执行按需阅读，提取目标、验收标准与依赖 |
| **Issue** | 携带 Issue 编号（如 `#102`） | 运行 `gh issue view <num>` 或读取关联文档，提取问题背景与复现步骤 |
| **空输入** | 用户仅输入 `/nk-work` 无参数 | 读取 `docs/current.md` 中 `## 下一步` 的第一项作为认领目标；若无下一步则提示用户指定 |
| **直接需求** | 自由文本描述，无 Plan 与 Issue | 按下述“直接需求规模分流表”评估并分流 |

---

## 二、直接需求规模分流 (Direct Request Triage)

当接收到无预设 Plan 的自由文本需求时，根据改动规模进行分流，避免在未经规划的大型需求上盲目开工：

| 规模档位 | 典型特征 | 处理动作 |
| :-- | :-- | :-- |
| **微小改动 (Trivial)** | 涉及 1~2 个文件、纯局部修复、错误信息修正、类型标注微调 | 直接在当前会话中执行测试先行与实现，完成后按 `nk-commit` 提交 |
| **中小改动 (Small-Medium)** | 涉及单个模块内的功能补齐、改动范围清晰（3~5 个文件内） | 在主对话中快速列出 2~4 个步骤的任务清单，逐项实现并自测，单次或分次提交 |
| **大型改动 (Large/Architectural)** | 跨模块重构、涉及核心数据结构变更、增加全新外部依赖、边界模糊 | **不直接执行**；建议用户先调用 `/nk-brainstorm` 澄清范围，或调用 `/nk-plan` 输出实施计划 |

---

## 三、Plan 文档按需阅读法 (Selective Reading)

当根据 Plan 实施时，**严禁一次性全文通读超长 Plan 文档**（避免占用宝贵上下文并稀释注意力）：

1. **结构扫描**：先读取 Plan 的目录结构或概览章节，了解本次特性的核心目标与当前单元的上下文位置。
2. **靶向精读**：只针对性读取**当前认领实施单元（U-ID）的正文**、其直接依赖的上游单元产物、以及该单元明确标注的验证标准。
3. **关注边界与推迟项**：重点查看 Plan 中的“范围边界（Out of Scope）”与“推迟到实现时决定的问题”，确保不越权实现范围外内容，不与架构既定约束冲突。

---

## 四、开工前置条件核实 (Preconditions Check)

在动手编写测试或代码前，快速核查以下前置条件：
1. **依赖就绪**：前置单元所承诺的代码、接口或数据文件是否已合并存在；
2. **环境可运行**：构建工具链与单测运行器（如 `cargo test`、`npm test`、`pytest`）是否可在当前环境执行；
3. **现场干净**：当前工作区不存在非本会话的冲突脏文件。
