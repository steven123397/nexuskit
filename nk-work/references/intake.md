# 任务输入与范围判定 (Intake)

本文件规范 `/nk-work` 如何解析输入、分流处理直接需求、核实 Plan 充分性以及按需阅读 Plan 文档。

---

## 一、输入类型与解析

| 输入类型 | 判定特征 | 解析动作 |
| :-- | :-- | :-- |
| **Plan 单元** | 携带 U-ID（如 `U2`）或 Plan 文件路径加单元号 | 定位 Plan 文件，先做充分性判断，再执行按需精读，提取目标与验收标准 |
| **Issue** | 携带 Issue 编号（如 `#102`） | 运行 `gh issue view <num>` 或读取关联文档，提取问题背景与复现步骤 |
| **空输入** | 用户仅输入 `/nk-work` 无参数 | 读取目标仓库 `docs/current.md` 中 `## 下一步` 的第一项作为认领目标；若无下一步则提示用户指定 |
| **直接需求** | 自由文本描述，无 Plan 与 Issue | 按下述“直接需求规模分流表”评估并分流 |

---

## 二、直接需求规模分流 (Direct Request Triage)

当接收到无预设 Plan 的自由文本需求时，根据改动规模进行分流，避免在未经规划的大型需求上盲目开工：

| 规模档位 | 典型特征 | 处理动作 |
| :-- | :-- | :-- |
| **微小改动 (Trivial)** | 涉及 1~2 个文件、纯局部修复、错误信息修正、类型标注微调 | 直接在当前会话中执行测试先行与实现，完成后按 `nk-commit` 规则提交 |
| **中小改动 (Small-Medium)** | 涉及单个模块内的功能补齐、改动范围清晰（3~5 个文件内） | 在主对话中快速列出 2~4 个步骤的任务清单，逐项实现并自测，单次或分次提交 |
| **大型改动 (Large/Architectural)** | 跨模块重构、涉及核心数据结构变更、增加全新外部依赖、边界模糊 | **建议先调用 `/nk-plan`（或 `/nk-brainstorm`）规划技术方案，由用户决定** |

---

## 三、Plan 充分性判断 (Plan Sufficiency Check)

在正式按 Plan 开工前，快速核查 Plan 是否达到可实施标准：
1. **方向 vs 实施方案**：若文档仅表达了业务期望或需求意向（仅有 Product Contract），缺少具体的数据结构、接口契约与实施单元划分，或者纯属探讨性记录，**不应强行开工，应退回 `/nk-plan` 补全技术规划**。
2. **验证标准是否具备可执行性**：检查当前单元的验收标准是否具体（例如是否有明确的输入输出对、预期的错误码、具体的断言标准），而不是仅有“校验正确”等模糊措辞。
3. **前置条件与现有代码的一致性**：Plan 依赖的基础代码、上游单元产物若在代码库中不存在或与当前真实代码产生根本矛盾，应停下向用户报告阻断，不凭空捏造与 Plan 契约相悖的替代实现。

---

## 四、Plan 文档按需阅读法 (Selective Reading)

当根据 Plan 实施时，**不一次性全文通读超长 Plan 文档**（避免占用宝贵上下文并稀释注意力）：

1. **结构扫描**：先读取 Plan 的目录结构或概览章节，了解本次特性的核心目标与当前单元的上下文位置。
2. **靶向精读**：只针对性读取**当前认领实施单元（U-ID）的正文**、其直接依赖的上游单元产物、以及该单元明确标注的验证标准。
3. **关注边界与推迟项**：重点查看 Plan 中的“范围边界（Out of Scope）”与“推迟到实现时决定的问题”，确保不越权实现范围外内容，不与架构既定约束冲突。

---

## 五、开工前置条件核实 (Preconditions Check)

在动手编写测试或代码前，核对以下环境条件：
1. **依赖就绪**：前置单元所承诺的代码、接口或数据文件是否已合并存在；
2. **环境可运行**：构建工具链与单测运行器（如 `cargo test`、`npm test`、`pytest`）是否可在当前环境执行；
3. **脏文件隔离（K8）**：已识别并确认当前工作区的外来脏文件，本次工作将其严格排除在外、不予暂存或提交。
