# 非代码工件交付规范 (Non-Code Work)

本文件规范当实施单元的产出物为配置、文档、规则或基础设施描述等非代码文件时的执行与验证方式。

---

## 一、非代码工件的范畴

* **项目配置文件**：YAML/JSON/TOML 配置、环境变量模板（`.env.example`）；
* **构建与 CI/CD 流程**：GitHub Actions 工作流、Dockerfile、发布打包脚本；
* **文档与规范**：系统架构文档、操作说明手册、接口契约 Schema；
* **规则与策略**：Agent 规则文件（`AGENTS.md`）、代码分析规则。

---

## 二、非代码工件的验证标准 (Verification)

非代码改动不能因“不是源码”而跳过验证，必须依据工件类型建立等效的确定性验证手段：

| 工件类型 | 验证手段 | 证据产出 |
| :-- | :-- | :-- |
| **结构化配置 (JSON/YAML/TOML)** | 使用解析器工具或校验脚本解析语法（如 Python `yaml.safe_load`、`jq .`） | 解析成功退出码 0，无语法格式报错 |
| **CI/CD 与容器 (Actions/Docker)** | 运行本地静态检查或 dry-run 验证（如 `actionlint`、`docker compose config`） | 配置有效性检验输出 |
| **接口契约 (OpenAPI / Schema)** | 运行 Schema Validator 对比示例 Payload 是否合法 | 模式校验通过断言 |
| **Markdown 与文档** | 核验所有内部相对链接与文件引用路径是否存在，语法是否合法 | 链接可达性走查结论 |

---

## 三、提交与节奏约定

* 若非代码工件是随同功能代码一同演进的（如新增代码连带修改了配置文件），必须依据 R1 与代码、测试**原子化一次性提交**。
* 若本次实施单元本身即为纯配置/文档调整任务，经上述验证通过后发起提交，并在提交说明正文中注明校验命令与通过证据。
