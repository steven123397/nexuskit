# 子代理协作机制 (Subagents)

本文件规范 `/nk-work` 中使用子代理（Subagent）辅助执行时的任务封装、协作边界与主会话提交职责。

---

## 一、子代理适用场景与定位

在支持派发子代理的客户端中，子代理不是默认流水线步骤，而是作为主会话的得力工具，适用于以下场景：
1. **隔离调查**：针对疑难代码逻辑或大型库的 API 接口进行独立的阅读与验证；
2. **全新上下文执行**：主会话已积累较多上下文时，派发一个具备干净上下文的子代理去专注实现某个具体的算法或模块实现单元；
3. **并行静态探索**：并行检索多个模块的依赖关系。

---

## 二、任务包定义 (Task Package)

当主会话向子代理派发任务时，必须提供清晰自洽的任务包定义，包含：
* **明确目标**：实施单元的目标与预期行为；
* **涉及文件与边界**：明确规定可修改的文件范围及严禁触碰的公共接口；
* **既定约束**：遵循的项目既有风格、命名惯例及 [`../../conventions/`](../../conventions/) 中的共享约定（相对本文件目录解析）；
* **验证标准**：具体的测试命令、预期覆盖用例与成功判断依据。

---

## 三、协作底线纪律

### 1. 子代理不执行 `git commit`
* 任何派发的子代理**不在隔离工作区或主工作树中直接执行 `git commit`**。
* 子代理的唯一任务是产生代码修改、运行验证，并将**改动文件清单与测试通过证据**回传给主会话。

### 2. 主会话核对实际工作树
主会话在收到子代理的完成回报后，必须执行以下核对步骤：
1. 运行 `git status` 与 `git diff`，核查实际改动文件是否与任务包约定一致，是否存在范围越界或残留调试代码；
2. 在主环境中**亲自执行一次测试验证命令**，捕获真实的成功退出码；
3. 核实无误后，由主会话读取 [`../../nk-commit/SKILL.md`](../../nk-commit/SKILL.md) 规则统一发起原子化提交。

## 附录：共享目录下的非默认并行（谨慎使用）

若在极少数情况下存在多个完全互不依赖、修改文件完全互斥的子任务：
* 可由主会话派发多个只读或独立改动子代理；
* 主会话必须严格串行收网：逐一核对改动、逐一运行测试、按 R1/R6 逐一发起带有各自 U-ID 的提交。
