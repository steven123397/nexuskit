# 审计模式细则

> 路径解析：本文件中 `../../conventions/`、`../../nk-commit/` 相对于本技能目录解析；`docs/solutions/`、`docs/current.md`、`CONCEPTS.md`、`AGENTS.md` 指目标仓库中的文件。

对照当前代码库审计 `docs/solutions/` 与 `CONCEPTS.md`，让知识库保持可信。报告与修正后的文档集是交付物。

## 1. 范围与调查

**范围**：候选为 `docs/solutions/` 下全部 `.md`。范围提示（目录名、frontmatter 的 `module`/`component`/`tags`、文件名、内容关键词）按此顺序收窄；匹配不上时报告未命中并停止，不擅自扩大为全量。空库时如实说明，并建议先用沉淀模式积累。

**逐条核对**（每条目对照当前代码库）：

- 引用的路径/类/模块是否仍在；推荐方案是否与代码现状一致；代码片段是否过时；
- 条目声明了 `retire_when` 时，按其描述的方式检查外部条件是否已满足（结果与检查日期记入报告，不写回条目；来源不可达时如实记录"未能检查"）；
- 条目点名的指导文件（某技能的 SKILL.md、runbook、指令文件）是否与条目矛盾——只比较条目点名的文件，不主动搜指导层，也不编辑指导文件，矛盾在报告中列出；
- 条目提到的领域术语，`CONCEPTS.md` 是否定义且仍准确（只收集信号，此阶段不改）。

**集合层面**：条目间的重叠、取代（旧窄条目被新条目涵盖）与矛盾。矛盾会主动误导读者，处理优先级高于单条过期。

**子代理**：3 条以上独立条目可派并行调查子代理（只读，返回证据与建议动作）；相互重叠或同根因的条目放在一起调查。客户端不支持子代理时由主会话依次完成。子代理提示词中写明：用平台的文件搜索/读取工具做调查，不编辑任何文件。

## 2. 分类与执行

每条目恰好一个结果：

| 结果 | 含义 | 动作 |
| :-- | :-- | :-- |
| Keep | 仍然准确有用 | 不改动，不留"已审阅"痕迹字段 |
| Update | 方案仍正确，引用漂移（路径、命名、链接、元数据） | 就地修正 |
| Consolidate | 多条重叠且均正确 | 独有内容并入基准条目，删除被并入者 |
| Replace | 旧指引已误导，且能写出可信继任 | 写继任条目后删除旧条目 |
| Delete | 不再有用、适用或无独有内容 | 删除文件——git 历史即归档 |

容易判错的规则：

- **年龄不等于过期**：仍与代码一致的旧条目是 Keep，年龄只是"更仔细检查"的提示。
- **不可验证不等于错误**：仓库无法佐证的断言（外部服务行为、运维实践）不是因此就错；只在代码明确相反时行动，无法佐证但合理的保留，并在报告中注明验证缺口。
- **Update / Replace 边界**：改写"推荐什么"是 Replace 不是 Update。Replace 需要真证据；证据不足时在 frontmatter 加 `status: stale`、`stale_reason` 与 `stale_date`，并建议下次遭遇该领域时用沉淀模式重建。
- **Consolidate 的检索价值测试**：半年后检索该主题的人，分开放是受益还是只增加漂移面？同一问题的两份文档终将漂移；不同子问题的两份条目即使引用同一文件也应分开放。
- **描述性漂移与实现冲突分开**：有独立证据支撑的指导，不因实现不再满足它而变假——按指导证据分类，把"代码未遵循既有指导"作为疑似产品回归写进报告，不在此改代码。

**删除需要正面证据（关键保全规则）**：

- 代码被删不构成删除理由：文件没了只证明实现没了，不证明问题域没了（token 文件删了，会话管理可能换了实现仍在）；
- Delete 前两查：问题域是否仍活跃（仍活跃则 Replace 不是 Delete）；入站引用——装饰性引用（顺带提及）可删并顺手清理，实质性引用（引用方依赖其内容）指向 Replace 或收窄保留，说不清则标 stale；
- 不确定时保留。自动删除（无需向用户确认）只在三者同时成立：实现曾在本仓且已消失（或条目已被完全取代/明显冗余）、问题域已消失（被取代时基准条目已包含其全部指导——逐句核对，主题重叠不算覆盖）、入站引用不存在或明确是装饰性的。

**值得性清理（仅在用户明确要求时）**：常规审计只判断准确性（是否仍然真实、是否仍独立）。当用户明确要求"清理/精简"知识库时，才追加值得性判断——条目的推理论证是否已被仓库内其他产物（测试、代码注释、指令文件、其他条目）的原话覆盖。覆盖成立需要点名产物并引用其原句，主题重叠不算覆盖；"不可验证不等于错误"仍然成立。这类删除或裁减一律列入 Recommended 交用户定夺，不自动执行。

**执行要点**：

- Consolidate 由主会话直接合并（文档都已读过），并入基准条目的自然位置而非简单追加；删除被并入条目并清理引用。
- Replace 的继任条目按 [`../../conventions/solution-schema.md`](../../conventions/solution-schema.md) 模板写，写后跑两份自检清单（[`frontmatter-checklist.md`](frontmatter-checklist.md)、[`claims-checklist.md`](claims-checklist.md)）。
- 移动条目（仅当目录与 frontmatter 分类明确不符，且内容证明是目录放错）用 `git mv` 并重写入站引用，移动后复查该条目的出站相对链接。
- 不为错别字或措辞改动条目（no churn）。

**提问**：无争议动作直接执行；Delete 未过上面的门槛、Replace、Consolidate 基准不明确时，按 [`../../conventions/decision-autonomy.md`](../../conventions/decision-autonomy.md) 批量选项提问；大范围审计分批执行并在批间确认。无人值守时：安全动作直接执行，争议动作标 stale 并列入报告 Recommended，同时在 `docs/current.md` 登记 `[待确认]`。

## 3. 术语对账与整库初建

按 [`../../conventions/concepts-vocabulary.md`](../../conventions/concepts-vocabulary.md) 执行，审计模式持全操作集（Add / Refine / Fold / Scrub / Retire）：

- 汇总调查中标记的领域术语与 `CONCEPTS.md` 对账，逐条核对既有词条是否仍满足准入标准、是否漂移；
- **删除需要正面证据同样适用于术语**：实现被删不构成 Retire 理由；拿不准保留；
- 全量审计覆盖整个文件，收窄范围只动该领域的词条。

**整库初建（bootstrap）**：老项目尚无 `CONCEPTS.md`，或用户明确要求建立完整术语表时，从**声明的领域模型**提炼核心名词——schema、核心类型、主模型、顶层领域文档，不做全代码库漫游；每条都应满足"新工程师不定义就读不懂"，不凑数。沉淀模式的即时写入只覆盖新术语，老项目的核心名词靠这一次初建补齐。

## 4. 报告与提交

**报告直接呈现给用户，是交付物**，分两段：

- 摘要块：扫描数、Keep / Update / Consolidate / Replace / Delete / 标 stale 各多少；`CONCEPTS.md` 一行结果（无变化也要写明"扫描，无合格变更"）。
- **Applied**：每个成功写入的文件——分类、证据、动作（Consolidate 写明基准与删除者）。
- **Recommended**：未执行的——写入失败的、证据不足标 stale 的、疑似产品回归、与指导文件的矛盾、可见性建议。

报告默认留在对话中，不落地成长期文件（产物去向遵循 [`../../conventions/artifact-lifecycle.md`](../../conventions/artifact-lifecycle.md)）；用户要求留存时按该约定决定位置。

**提交**：读取 [`../../nk-commit/SKILL.md`](../../nk-commit/SKILL.md)。只暂存本次审计修改的文件。工作区有在途代码工作时，审计改动默认留在工作区，随下次代码提交入库（R2）；用户明确要求立即入库时，发起一次纯文档维护提交，提交信息概括动作（如"更新 3 条过期条目、合并 2 条重叠、删除 1 条失效"），风格遵循项目惯例。

**可见性检查**：每次审计结束后按 [`../../conventions/artifact-lifecycle.md`](../../conventions/artifact-lifecycle.md) 第二章检查 `AGENTS.md` 入口指引（同沉淀模式第 5 阶段）。
