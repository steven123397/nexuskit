# 发想记录格式

本文件定义 nk-ideate 产出文件的内容与 Markdown 写法。在写入时（`post-ideation-workflow.md` §4.1）读取。

## 发想记录包含什么

一份发想记录是：一组排好序、经过批判的候选，这些候选所对照的扎根材料，以及被淘汰内容的记录。它是面向人的探索文档，不是需求文档或 plan——围绕想法及其依据，不写实施细节。

### 元数据（YAML frontmatter）

* **date** —— 写作日期（YYYY-MM-DD）。
* **topic** —— kebab-case 的主题短名。
* **focus** —— 给出关注点时填写；开放式时省略。
* **mode** —— `repo-grounded`、`elsewhere-software` 或 `elsewhere-non-software`。这是文件内的机器可读字段，不在会话中向用户展示。

**没有状态字段——文档上没有，每个想法上也没有。** 发想记录是某一时刻的探索产物，不是被追踪的工作项：没有 `active → completed` 生命周期，也没有逐想法的"已探索"标记。在文档里记录可变的工作进度会形成第二个会漂移的事实来源——一个想法后来是否被推进，可以从下游产物（采纳了它的 plan）得知，不在这里重复。文件何时删除由 `../../conventions/artifact-lifecycle.md` 的发想记录一行决定。

### 扎根背景（Grounding Context）

这些想法所对照的 Phase 1 扎根摘要——仓库模式下标为 "Codebase Context"，仓库外模式下标为 "Topic Context"。

### 主题轴（Topic Axes，条件性）

Phase 1.5 的 3~5 条轴，每行一条。Phase 1.5 被跳过时，用一行记录原因（`Decomposition skipped — atomic subject` 或 `Decomposition skipped — surprise-me mode`）。不适用时整个省略本节。

### 排序后的想法（Ranked Ideas）

留存的候选，按排序列出。每个想法包含：

* **标题**
* **描述** —— 具体说明。
* **轴** —— 这个想法针对的主题轴。拆轴被跳过时省略。
* **依据** —— 带标签：`direct:`（引用的证据）/ `external:`（具名的已有做法）/ `reasoned:`（写出来的第一性原理论证）。
* **理由** —— 依据如何与这一步的意义相连。
* **代价** —— 取舍或成本。
* **置信度** —— 0~100%。
* **复杂度** —— 小 / 中 / 大。

想法卡片是用来完整阅读以选择方向的，不要把实质内容藏起来。

**示意图——按想法的形态决定，而不是按文字是否清楚决定。** 放得恰当的示意图能让人在浏览一组候选时更快理解一个方向。逐个留存决定——可能没有、少数或多数需要；没有配额也没有上限。

注意一个陷阱：文字总能表达想法（这是下面的硬规则），而作为以文本为主的推理者，你倾向于读自己的文字、判断它"很清楚"、于是认为不需要图——这会悄悄少产出真正有帮助的图。所以"文字已经清楚"永远不是跳过的理由。真正的问题是这个想法*取决于*什么，以及那个东西有没有一种画出来比写出来更快传达的形态。

* **取决于某种结构 → 倾向于画图。** 部件之间的关系、流程或顺序、前后对比、结构布局、类比映射（尤其是跨领域想法）、数量比较。即使文字很清楚，图也能更快传达这些——并且应该展示*依据*或*为什么重要*，而不是复述标题。新功能概念常常属于这一类。
* **只有一个要点、没有可画的结构 → 不画。** 改名、改文案、"处理空值情况"、直接替换一个库——没有可以用图增加的形态；画了就是装饰。

装饰——没有形态可展示、或只是复述标题的图——就是失败，一张两张都算。真正展示了想法形态的图从来不是装饰，不管有多少个想法需要它。

加图时的两条约束：

* **保持在想法的高度——示意性的，不是规格。** 这和 plan 或需求里的图正好相反：plan 中的图是权威内容；发想里的图是对尚未确定的方向的示意性概览。保持概念化（对比、类比、大致流程）。详细架构、时序图和线框图属于方向选定之后的 `nk-brainstorm` / `nk-plan`，不属于这里。
* **文字要能独立成立。** 忽略图的读者仍然能得到完整的想法及其依据。图加速理解，但不承载别处没有的内容。

Markdown 中用围栏 mermaid 代码块画图（形态合适时）。

### 淘汰摘要（Rejection Summary）

一张被考虑后淘汰的想法表，每个附一行理由。某条轴在补派之后仍然零留存时，单独记一行，让覆盖缺口可见而不是悄悄缺失。

## Markdown 写法

* 文件顶部是 YAML frontmatter（`---` 包围）。
* 标题保持 ASCII 或简单文字，便于锚点稳定。
* 文件引用一律用仓库相对路径。
* 不混入 HTML。
* 不按固定列宽硬换行：每句一行，或每段一整行。
* 有 5 个以上结构一致的条目时用表格（如淘汰摘要）；3~5 个、每个有几行文字时用列表；叙述性内容用段落。

## Markdown 骨架

```markdown
---
date: YYYY-MM-DD
topic: <kebab-case-topic>
focus: <可选的关注点>
mode: <repo-grounded | elsewhere-software | elsewhere-non-software>
---

# Ideation: <标题>

## Grounding Context
[Phase 1 的扎根摘要——仓库模式为 "Codebase Context"，仓库外模式为 "Topic Context"]

## Topic Axes
[Phase 1.5 的 3~5 条轴，每行一条；或一行 `Decomposition skipped — ...`。不适用时省略本节。]

## Ranked Ideas

### 1. <想法标题>
**描述：** [具体说明]
**轴：** [针对的主题轴——拆轴被跳过时省略]
**依据：** [`direct:` / `external:` / `reasoned:` —— 引用、出处或写出的论证]
**理由：** [依据如何与这一步的意义相连]
**代价：** [取舍或成本]
**置信度：** [0-100%]
**复杂度：** [小 / 中 / 大]

## Rejection Summary

| # | 想法 | 淘汰理由 |
|---|------|----------|
| 1 | <想法> | <理由> |

[适用时，把轴覆盖缺口单独记一行：]
| - | axis: <name> | recovery skipped (cap reached) — 这条轴没有留存 |
```

## 不写过程记录

发想记录中不写工程过程元数据——不写"在第几阶段得出"、不写指向其他技能的"下一步"、不写斜体来源说明。读者要的是想法及其依据。下一步写在 `docs/current.md`，不写在这里。
