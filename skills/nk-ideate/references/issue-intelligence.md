# Issue 分析（Phase 1，条件性）

当 Phase 1 第 4 步适用时读本文件，即 Phase 0.2 识别出 Issue 分析意图时。`grounding.md` 定义四步顺序（扫描 → 降级或定范围 → 聚类 → 等待）；本文件定义每次调用的内容，以及范围问题如何构造。

这条线对任何可访问的追踪器都有效——GitHub、Linear 或 Jira。按能力探查（连接器/MCP、有文档的 API 或有文档的 CLI），不要假定某个特定程序存在。缺少某个程序或环境变量，不等于追踪器不可达。NexusKit 项目通常使用 GitHub Issues，首选 `gh`。

## a. 扫描调用

读 `agents/issue-intelligence-analyst.md`，派发一个通用子代理，以该提示、关注点、Phase 1 确定的 `<scratch-dir>`，以及"处于 **SCAN 模式**"的说明作为种子。

它探查追踪器访问，做一次有界的抓取，把抓取的数据持久化到 `<scratch-dir>/issue-scan.json`，返回分布、信号数和歧义评估。它**不**聚类。

扫描调用可以与其他 Phase 1 扎根代理并行。

## b. 降级标记

两种结果会在聚类调用之前结束这条线。两者都是"提示并继续"——永远不因此阻断运行：

* **首行是 `Issue analysis unavailable:` 标记**（追踪器不可达）—— 记录 `"{该消息}。继续进行常规发想。"`，继续其余扎根。
* **可用 Issue 少于 5 个** —— 注明 `"Issue 信号不足，无法做主题分析"`，继续。

两种情况下 Phase 2 都回退到六视角默认编队，而不是 4 个代理的 Issue 分析编队——**回退只重新推导被放弃的视角集合所决定的东西，别的什么都不重新决定。** 沿用 Phase 0.5 **已经确定的**规模状态——冲突解决*之后*哪些覆盖生效，以及原始总数或明确的留存数。不要重新读取请求里的原始信号：一个同时说了 `quick wins` 的 `go deep` 运行已经取消了 tactical，从原始信号重新推导会让已免除的门槛和降低的产量在最高深度的运行上复活。**只**重新推导视角数量决定的两个值——代理数和每个视角的分配——因为视角集合从至多 4 个主题变成了 6 个默认视角。编队变体见 `divergent-ideation.md`。不问范围问题。

## b. 范围问题（由编排者决定；至多一个问题）

读扫描的歧义评估。

**默认静默自动定范围。** 按 关注点 → 优先级（有填写时）→ 工作流状态 → 时间近度 的顺序组成范围。

**只有**在无法消除的歧义时才问**一个**阻塞式范围问题（提问方式见 `scope-gates.md` 开头）：存在两个或以上连贯、实质不同的范围，任何一次有意分层的抽样都无法公平代表。扫描结果没有歧义时完全跳过。

选项是扫描结果按分布得出的切片，外加一个始终存在的 **"对全部内容做有代表性的抽样"**，让用户可以不缩小范围。切片加上这个选项超出平台提问工具的选项上限时（有的客户端只接受 2~3 个明确选项，有的接受 4 个），展示分量最大的几个切片，其余并入代表性抽样选项，或退回到对话中的编号列表。**永远不要去掉代表性抽样选项。**

这是一个扎根/定主题范围的问题——与 Phase 0.2 的主题关卡（"Agent 要处理什么"）属于同一类，而不是 Phase 0.4 那种关于方案约束的问题。它计入"不超过 3 个问题"的额度，"给我惊喜"仍然可用。

## c. 聚类调用

以 **CLUSTER 模式**再次派发分析代理，传入确定的范围**和同一个 `<scratch-dir>`**，让它复用持久化的 `issue-scan.json`，而不是重新抓取。它返回按杠杆排序的主题和覆盖统计。

## d. 合并时必须保留的内容

合并后扎根摘要的 `Issue intelligence` 一节要包含主题概述（标题、描述、Issue 数、杠杆、趋势方向）**以及聚类调用的覆盖统计**——抓取数 / 可用数 / 分析数 / 排除数 / 未知剩余，以及任何 `>N` 下限。这份统计是"未穷尽覆盖"的披露；它必须传到 Phase 2 发想和 Phase 4 发想记录中，而不是在合并时丢掉。

主题按 `divergent-ideation.md` 中的 Issue 分析模式覆盖成为 Phase 2 的视角。

不支持子代理时，主会话依次完成扫描与聚类，遵循同一份分析提示中的抓取、统计和聚类规则。
