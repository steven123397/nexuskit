# 发想之后的流程

Phase 2 的发想代理返回、编排者把产出合并去重成总候选清单之后读本文件。Phase 2 完成之前不要读取。本文件中的相对路径相对本文件所在目录解析。

## Phase 3：对抗式筛选

批判地审视每一个候选想法。批判分两层——先由全新上下文的核查者核查，再由编排者裁定。全新上下文的核查优于自我批判：部分候选是编排者自己综合出来的，它带着完整的生成历史，存在锚定；没见过生成过程的核查者不受这种影响。

1. **依据核查（一个生成档子代理——见 `grounding.md` 的模型档位）。** 派发一个核查者，只给它合并后的扎根摘要（包括证据概要和档案文件路径——需要时它自己去读档案）和合并后的候选清单——不给任何生成历史。提示它去反驳：对每个候选，检查所述依据是否真正支持所主张的做法；`direct:` 引用的内容是否确实存在（仓库模式下读文件抽查）；`external:` 的已有做法是否真实且确有可比性；`reasoned:` 的论证是否成立。它对每个候选返回结论（sound / weak / refuted）和一行理由。`go deep`（Phase 0.5）下再派发第二个最高档批判者，关注新颖性与可行性，给它同样的全新上下文内容。

   **在核查者的派发内容中明确说明开会门槛，无论是否免除。** 默认情况下，也让它判断每个想法是否确实值得开会讨论；因为想法不是它写的，它的判断取代生成者的自我声明。**tactical 范围生效时（Phase 0.5），告诉核查者门槛已免除**，让它只判断依据。核查者在全新上下文中运行，不知道生成过程，不告诉它，它就不知道门槛已免除——漏掉这一点会让 tactical 运行的每个候选都被判为 `weak`。

   不支持子代理时，主会话在进入裁定之前，先只看扎根摘要和候选清单逐条做同样的反驳式核查，并在淘汰摘要中注明核查不是独立完成的。

2. **编排者裁定。** 编排者做最终取舍，参考核查者的结论但不受其约束——手头证据与某条结论矛盾时可以推翻，并在淘汰理由中说明。

核查者派发在修正调用后仍然失败时，退回到只由编排者筛选，并在淘汰摘要中注明这一降级。

本阶段不生成替代想法，除非是在明确地打磨。

每个被淘汰的想法写一行理由。

淘汰标准：
* 太模糊
* 无法行动
* 与更强的想法重复
* 没有扎根于给定的背景
* 相对可能的价值成本太高
* 现有工作流或文档已经覆盖
* 有意思，但更适合作为 brainstorm 的一个变体，而不是一项产品改进
* **没有理由——缺少写出来的依据**（子代理没有给出 `direct:`、`external:` 或 `reasoned:` 依据，或所述依据并不支持所主张的做法）
* **依据被核查推翻**（核查者发现引用的原文不存在、已有做法被曲解、或论证不成立——且编排者同意）
* **低于抱负门槛**（不值得团队讨论——tactical 范围生效时此条免除，见 Phase 0.5）
* **替换主题**（放弃或替换了发想的主题，而不是在它上面做文章——例如"转向无关领域"、"变成另一种组织"）
* **超出范围**（超出用户问的范围，而不是在范围内发想——例如用户问的是一个流程、阶段或区块，却提出对整个产品的改动）。只有依据明确支持这种扩展时才允许；默认淘汰或降级。

用一致的标准为留下的想法打分，权衡：扎根于给定背景的程度、**依据强度**（`direct:` > `external:` > `reasoned:`；都不排除，但在其他条件相同时直接证据得分更高）、预期价值、新颖性、务实程度、对未来工作的杠杆、实施负担、与更强想法的重叠，以及**轴分布**（Phase 1.5 产出了轴列表时）——其他条件相同时，覆盖多条轴的留存集合优于挤在一条轴上的集合。

**轴覆盖是清单层面的考量。** 定义了轴时，轴分布在整个留存集合上评估，而不是逐个想法评估。逐个筛选之后检查留存集合：轴覆盖不均、且在覆盖不足的轴上有更强的候选时，在提拔边缘候选时优先照顾分布。Phase 2 的补派应该已经为空轴产出了候选；这里只是在留存选择上做打磨。某条轴在补派之后（或因为补派达到 2 条上限）仍然零留存时，在淘汰摘要中注明这是有意的缺口，而不是疏忽。

目标产出：
* **请求中明确的留存数优先**——`top 3`，或小到无法分到各视角的总数；没有时，留下 5~7 个
* 留下太多时，再做一轮更严格的筛选
* 少于目标数时——默认运行为 5 个——如实报告，而不是降低标准

## Phase 4：写入并呈现发想记录

发想记录**自动**生成——持久化不是可选项。筛选之后写入文件，在会话中给出简要汇报。完整内容在文件里；会话中只展示定向用的摘要。

**检查点 B。** 写入发想记录之前，把留存清单连同关键背景（关注点、扎根摘要、淘汰摘要）写到 `<scratch-dir>/survivors.md`（Phase 1 记下的绝对路径）。尽力而为：写入失败时记录提示并继续；运行不依赖检查点。复用 Phase 1 生成的同一个 `<run-id>` / `<scratch-dir>`。

### 4.1 写入发想记录（自动，两种模式）

每次运行都写文件——不要等用户要求。只写 Markdown。

1. **确定目标目录。**
   * **仓库模式：** 确保目标仓库的 `docs/ideation/` 存在（不存在就创建）。
   * **仓库外模式，且 `docs/ideation/` 已存在：** 使用它。
   * **其他情况（无仓库，或仓库外模式且没有 `docs/ideation/`）：** 写到本次运行的临时目录 `<scratch-dir>`。**不要**写进用户的当前工作目录，也**不要**为与仓库无关的主题创建 `docs/ideation/`。告诉用户绝对路径，并说明这是临时位置（系统可能清理临时目录——要保留就移走）。
2. **确定文件路径：** `<dir>/YYYY-MM-DD-<topic>-ideation.md`（没有关注点时为 `<dir>/YYYY-MM-DD-open-ideation.md`）。
3. **读取格式约定**（推迟到此时才读）：`ideation-sections.md`。
4. **按约定写入文档。** `ideation-sections.md` 定义各节内容（元数据、扎根背景、主题轴、排序后的想法及每个想法的字段、淘汰摘要）与 Markdown 写法。
   * **写入失败时**（没有可写路径、权限问题）：告知失败并提供自定义路径（验证可写；创建父目录）。永远不要悄悄丢掉留存结果。

**续作：** 就地更新现有文件；保留之前的想法与淘汰摘要，在其基础上追加，而不是覆盖。

### 4.2 呈现简要汇报（不是完整发想记录）

完整的想法卡片、理由、代价和淘汰表都在文件里。**不要**在会话中复述它们——把整份发想记录当作聊天文字重印一遍，读者要先读一遍纯文本才能看到文件本身。只给一份紧凑的定向摘要：

* 一行说明数量和路径：例如 `写入 7 个排序后的想法（原始 36 个，淘汰 13 个），覆盖 5 条轴 → <绝对路径>`。
* 排序清单，**每个留存一行**：`1. <标题> · <轴> · 置信度 <高/中/低> · 复杂度 <小/中/大>`。
* 用一句话点出首选。
* 任何零留存的轴用一行注明（有意的缺口）。

这份排序清单同时是用户在 Phase 5 选择想法时引用的索引。

## Phase 5：下一步

用阻塞式提问工具（没有或出错时用编号选项）问下一步做什么，不要静默跳过。接受自由回答。

发想记录已经存在（Phase 4），所以菜单只关于*接下来做什么*——没有"保存"这一步。

**题干：** "发想记录已保存到 `<path>`。接下来？"

提供四个选项（标签自成一体，把区分性的词放在前面，截断时仍能区分）：

1. **用 `nk-brainstorm` 深入一个想法** —— 把选中的想法落成 plan 的需求部分；离开 nk-ideate。先问选哪个。
2. **先讨论或调整这些想法** —— 留在这里，在落地之前通盘考虑：调整或追问某个想法、比较几个想法，或组合/合并它们。先问想处理什么。
3. **结束会话** —— 读取 `../../nk-handoff/SKILL.md` 完成交接；发想记录随交接提交一起入库。
4. **完成——保留文件并停止。**

**附带提示（写在正文里，不占选项）：** "不想保留？说'丢弃'，Agent 会删除这个文件。"通过自由回答处理（见 §5.5）；只对本次新建的文件有效，永远不删除续作的或之前就存在的文件。

用户已经在回答中说明了想处理什么时（例如"深入表格工具那个"、"把高亮那个收紧一点"、"把表格和高亮合并"），跳过 §5.1 / §5.2 中询问处理对象的追问。

### 5.1 用 nk-brainstorm 深入一个想法

1. **确定想法**，按编号或名称（用户已经点名时跳过）。对照 Phase 4.2 的排序清单匹配。
2. **从编排者上下文中已有的想法实质内容构建一个聚焦的种子。** **不要**传整个文件——浪费且嘈杂（其他留存、扎根和淘汰表与定义这一个想法无关）。**也不要**只传一个文件指针——那会迫使 `nk-brainstorm` 重新打开文件、再提取一遍编排者已经掌握的想法。种子是需求描述的形状：

   > `<标题> — <描述>。依据：<依据/证据>。为什么重要：<理由>。已知取舍：<代价>。`

   依据/证据直接输入 `nk-brainstorm` 的压力测试，它就不必重新推导已知的内容。附一行来源指针：`（来自 nk-ideate：<path>，想法 "<标题>"）`——它记录来源，也让 brainstorm 需要时可以取相邻细节，而不被迫阅读任何东西。在 plan 的 frontmatter 中，这个路径可以作为 `origin`。
3. **读取 `../../nk-brainstorm/SKILL.md`**，以这个种子执行。保存的文件已经是记录——不需要额外写入。同一会话继续时，发想记录留在工作区，随后续的提交或交接提交入库（见 `../../conventions/commit-cadence.md` R2/R4），此处不单独提交。

**仅仓库模式：** **不要**跳过 brainstorm 直接进入 `nk-plan`——`nk-plan` 需要一个经过 brainstorm 的 Product Contract。仓库外模式下，发想本身就是合理的终点；brainstorm 是对一个想法可选的进一步展开，而不是实施阶梯上必经的下一级——这些模式下根本没有实施阶梯。

### 5.2 先讨论或调整这些想法

这一步留在 nk-ideate 内——不交给其他技能。这是"落地之前通盘考虑"的一步，也是发想的正常结果：看到几个都很强的候选、想要斟酌一下，比立刻选定一个更常见。编排者仍然掌握完整的扎根和生成背景，可以对每个留存通盘推理——这正是这些背景派上用场的地方。这里的工作要么是**单个想法**（打磨或追问一个），要么是**跨想法**（比较、组合或合并几个）；不要强迫用户先点名一个想法才能开始。

1. **确定用户想处理什么、怎么处理。** 有措辞就从中推断；否则问一个开放问题（"想处理什么？"），而不是假设只有一个想法。范围可以是一个想法、一部分或全部。
2. **按意图处理：**
   * **提问 / 比较**（"为什么置信度高？"、"这和某某产品比怎么样？"、"哪些有重叠？"、"哪两个最接近？"）—— 在对话中回答，依据想法的依据和 Phase 1 扎根。可以涉及一个或多个想法。**不改写文件**，除非讨论产生了用户想记下来的改动。
   * **调整**（"缩小范围"、"去掉导入那部分"、"围绕 X 重新定框"）—— 按讨论修改该想法的定框、范围或依据，然后**改写保存的文件**，让发想记录保持最新。
   * **深化**（"展开二阶效应"）—— 扩展某个想法的分析；只有用户想保留时才写进文件。
   * **组合 / 合并**（"把表格和高亮合并"、"把 2 并入 5"）—— 把指定的想法综合成一个：写出统一的标题、描述和依据，取材于每个来源想法（保留最强的依据；合并它们的证据）。改写文件时，**用合并后的单个条目替换被合并的来源条目**——不要把原条目与合并结果并列——并重新编号排序清单。重新评估合并后想法的轴和置信度，而不是照抄某个来源的。如果某个来源想法实际上因此退出，在淘汰摘要中注明这次合并。
3. **只在有改动时改写。** 只有想法内容确实变化时（调整、深化并保留、合并）才改写文件——提问和比较本身不改动文件。
4. **回到 Phase 5 菜单。** 通常用户接下来会对打磨或合并后的想法做 brainstorm（§5.1）、继续讨论或结束。

### 5.3 结束会话

读取 `../../nk-handoff/SKILL.md` 并执行。本次会话新建或修改的发想记录属于规划产出，与 `docs/current.md` 一起组成该会话唯一的一次交接提交。临时目录中的文件（非仓库主题）不入库，只在汇报中给出路径。

### 5.4 完成

文件已经写好，没有保存步骤。

* **在 git 仓库内：** 不单独提交发想记录（遵循 `../../conventions/commit-cadence.md` R2）；告诉用户文件留在工作区，会随下一次提交或会话交接提交一起入库。
* **临时目录或非仓库文件：** 直接给出路径。

然后说明路径并结束——不回到菜单。

### 5.5 丢弃（自由回答）

只对**本次新建**的文件有效：删除它，确认已删除，然后结束。在**续作**运行中（就地更新了之前就存在的文件），**不要**删除——告诉用户 `<path>` 上的现有文档仍在，不提供任何破坏性操作。丢弃永远不是默认行为；只在用户明确要求时发生。

运行结束时不删除临时目录（`<scratch-dir>`）——它保存着同一会话后续发想会跨 run-id 复用的网络调研缓存（见 `web-research-cache.md`）、检查点 A/B 文件、证据档案，以及（无仓库时）发想记录本身。清理交给操作系统。

## 质量标准

结束之前检查：

* 想法集合扎根于给定背景（仓库模式下是代码库；仓库外模式下是用户提供的材料）
* **每个留存想法都有写出来的依据**（`direct:`、`external:` 或 `reasoned:`），且依据确实支持所主张的做法——伪装成抱负的推测已被淘汰并附理由
* 留存想法所依赖的 `direct:` 依据已对照仓库（或提供的材料）核实——由生成代理的核实阅读或 Phase 3 核查者完成——而不是照单全收
* **每个留存想法都值得开会讨论**，除非 tactical 范围生效并免除了门槛
* **没有留存想法替换了主题**，而不是在主题上做文章
* Phase 1.5 产出了轴列表时，留存集合分布在多条轴上而不是挤在一条轴上——任何零留存的轴都在淘汰摘要中注明为有意的缺口，而不是悄悄缺失
* 候选清单是在筛选之前生成的
* 保持了"大量想法 → 批判 → 留存"的原始机制
* 使用了子代理时，它们提升了多样性，而没有替代核心流程
* 每个被淘汰的想法都有理由
* 留存想法明显好于一份天真的"给我点子"清单
* 发想记录在两种模式下都自动写入（Phase 4）——有 `docs/ideation/` 时写在那里，否则写在临时目录，永远不写在用户的当前工作目录
* 会话中展示的是简要摘要，不是完整发想记录的复述
* 要落地一个想法时，走 `nk-brainstorm`（带实质种子，而不是整个文件），而不是直接进入实施
