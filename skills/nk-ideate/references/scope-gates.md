# 续作检查与范围关卡（Phase 0.1–0.6）

Phase 0 开始时必读，任何扎根派发之前完成。本文件定义：近期发想记录的续作检查、主题识别关卡与范围提问、模式分类、仓库外主题的材料检查、关注点与数量的解读（含 tactical 档位），以及成本提示。

## 提问方式（适用于下面每个关卡）

有阻塞式提问工具就用它（按能力匹配，不按某个客户端的工具名）；工具列表里没有、或调用出错时，在对话中给编号选项。不要静默跳过问题。

遵循 `../../conventions/decision-autonomy.md`：互不依赖的问题合并在一轮里问（最多 3 个），自然存在选项时用单选并标注推荐项。无人值守时采用推荐项继续，并在最终汇报里说明做了哪个选择。

## 0.1 近期发想记录

在目标仓库的 `docs/ideation/` 下找 30 天内创建的发想记录（`*.md`）。这是仓库模式的便利功能：没有 git 仓库、或还没确定是仓库模式时跳过，不要在 0.3 分类之前就让运行失败——仓库外主题和无仓库运行写入临时目录，不碰 `docs/ideation/`。

当一份旧记录的主题、路径或子系统与本次关注点重叠，或者本次请求是开放式的且近期恰好只有一份明显的记录时，视为相关。基于 Issue 的发想和普通发想是不同主题，不跨越这条线续作。

存在相关记录时，问用户是接着那份做还是重新开始。接着做：读取它，概括已经探索过的内容，保留原有想法与淘汰摘要，**更新原文件**而不是新建。

## 0.2 主题识别关卡

在分类模式或派发扎根之前，先确认发想的主题是否可识别。每个下游代理都要知道自己在处理什么；如果合理的子代理会对"主题是什么"产生分歧（`改进`、`点子`、`生日蛋糕` 这类光秃的词），产出会四处发散。

**提问原则（本阶段与 0.4 通用）：**

* 提问只为补足子代理运作所需：可识别的主题（本阶段）和足以说出具体内容的材料（0.4，仅仓库外模式）。不问别的。
* 不问方案方向、约束、受众、语气或成功标准，这些归 `nk-brainstorm`。
* "给我惊喜"始终是正式选项，不是给说不出主题的用户的兜底。发想本来就允许从零开始。
* 主题一旦可识别、或用户选择了"给我惊喜"，立即停止提问。0.2、0.3、0.4 与 Phase 1 的 Issue 范围提问累计超过 3 个，说明发想不是合适的流程，可以建议改用 `nk-brainstorm`。

**识别 Issue 分析意图（仅仓库模式；它本身确定了主题）。** 需要明确提到 Issue 追踪器或其中的报告：`open issues`、`issue 模式`、`issue 主题`、`用户在报什么问题`、`bug 报告`，或具名的追踪器（`github issues`、`linear issues`、`jira tickets`）。此时主题就是"追踪器中的 Issue"。对任何可访问的追踪器都有效——GitHub、Linear 或 Jira，不强制 GitHub。带着 Issue 意图标记进入 0.3。

只是把 bug 当作关注点时不触发：`auth 里的 bug`、`修登录问题`、`注册 bug`、`认证里最严重的 3 个 bug`——这些是普通发想的关注点，不是分析追踪器。单独一个 `bugs` 且没有追踪器措辞时，交给下面的模糊性检查。

组合出现时（如 `认证方面前 3 个 issue 主题`、`结账相关最多的 bug 报告`）：先识别 Issue 意图，数量覆盖在 0.5 处理，剩余部分是关注点。关注点缩小哪些 Issue 相关，数量覆盖控制留下的想法个数。

**判断主题是否可识别。**

检验方法：只看这句请求的读者，能否知道 Agent 应该就什么发想？模糊与否取决于词语**指代什么**，不取决于长短：`browser sniff` 只有两个词，但很可能指一个功能（可识别，进入 0.3）；`quick wins` 也是两个词，但只指一种品质（模糊，提范围问题）。指向笼统品质、类别或占位的请求（`改进`、单独的 `bugs`、空请求）是模糊的；指出或很可能指出某个具体功能、概念、文档、流程或话题的请求是可识别的，不分领域。身处某个仓库并不能解决这个问题——任何仓库里的 `改进` 都会散落到开发体验、可靠性、功能、文档、测试和架构上；仓库在主题确定**之后**提供扎根材料，而不是提供主题本身。

**确实拿不准时（仓库模式）。** 对一个短语真有疑问时，一次廉价检查就能定：用文件搜索工具按文件名搜这个短语，或在 README/docs 中搜内容。仓库里有任何痕迹就算可识别；没有且仍然模糊就提问。其他情况倾向于提问——问一个问题的代价，远小于在分散的理解上派出十几个代理。

**范围问题。**

* **题干：** "要就什么发想？"
* **选项：**
  * "指定一个主题"
  * "给我惊喜——让 Agent 自己决定关注什么"
  * "取消——我换个说法"

路由：

* **指定** → 把用户的补充作为主题，再做一次可识别性检查。仍然模糊就再问一次，菜单里保留"给我惊喜"。只追问"主题是什么"，不追问"怎么解决"。
* **给我惊喜** → 标记为 **Surprise me 模式**，在下表列出的每个阶段套用对应差异。
* **取消** → 干净退出，告诉用户可以换个说法重新调用。

**Surprise me 模式的全部差异（集中在此处）。** Agent 从 Phase 1 的材料中发现主题，而不是使用用户指定的主题。这是一种正式模式。后续各阶段只写一句指向此处的提示，含义以本表为准。

| 阶段 | 差异 |
| :-- | :-- |
| 0.3 模式 | **确定性判断，跳过决策 1/2。** 当前目录在 git 仓库内 → 仓库模式；否则 → 仓库外软件主题。永远不会是非软件主题：没有主题，就无从推断命名、叙事或个人意图。不做模式歧义确认。 |
| 0.4 材料 | 路由到仓库外软件主题时**必须**有材料：既没有主题也没有仓库，Phase 1 无从发现任何东西。问一次；用户仍给不出 URL、描述或粘贴内容时，干净结束，让用户带上材料再调用。 |
| 模型档位 | 整个发想编队提到最高档——发现主题依赖判断力，这正是此模式的价值所在。 |
| 1 扎根 | 更深入，因为 Phase 2 要从 Phase 1 的返回中发现主题。仓库：按顶层目录抽样有代表性的文件，并查看近期 PR/提交活动，有界——有代表性，不求穷尽。仓库外：提取主题、反复出现的说法、张力与缺失，而不是复述用户的材料；把网络调研扩大到该领域的整体格局。 |
| 1.5 拆轴 | 跳过——没有确定的主题可拆。记为 `Decomposition skipped — surprise-me mode`。 |
| 2 生成 | 每个视角自选主题（见 `divergent-ideation.md`）；交叉组合承担原本由 Phase 1.5 负责的覆盖作用，预期 5~8 个组合而不是 3~5 个。不做轴覆盖补派。 |

用户随时可以打断，并带着具体主题重新调用来纠正方向。

## 0.3 模式分类

模式确定之前，不要解析或创建产出目录——仓库外和无仓库的运行根本用不到它。

把 0.2 确定的**发想主题**归入三种模式之一，用于决定派发路线。用户身处任何仓库都可能就与之无关的事情发想；身处临时目录也可能就脑子里的代码发想。

**Surprise me 捷径。** Surprise me 模式下跳过下面两个决策和歧义确认，套用 0.2 表中 `0.3 模式` 一行。用一句话说明选定的模式，然后进入 0.4。

对指定主题，依次做两个二选一决策：

**决策 1 —— 仓库内 vs 仓库外。** 优先看请求内容，其次看主题与仓库的契合度，当前目录是否在仓库内只作辅助证据。**仓库内**：请求提到仓库的文件、代码、架构、模块、测试或工作流，或主题受当前代码库限定；0.2 识别出的 Issue 意图一律是仓库内。**仓库外**：请求提到仓库里没有的东西——定价、命名、叙事、商业模式、个人决策、品牌、内容、市场定位——或者主题是创意、商业、个人性质且不涉及代码。

**决策 2（仅当决策 1 = 仓库外）—— 软件 vs 非软件。** 看**主题**是不是软件制品或系统，而不是看想法落在哪里。产品、应用、SaaS、网页/移动端界面、功能、页面或服务都是**仓库外软件主题**——即使想法本身关于文案、UX、转化率、定价、引导、视觉设计或该产品的定位。**非软件主题**只留给与任何软件制品无关的话题：独立于产品的公司或品牌命名、叙事与创意写作、个人决策、非数字化商业策略、实体产品设计。

对照：「提高我们注册页的转化率」→ 仓库外软件主题（主题是一个页面，即使想法可能是文案或转化优化）；「给我的新咖啡店起名」→ 非软件主题（主题是品牌，不是软件制品）。

用一句平实的话说明推断出的做法，借用主题本身的领域词（"落地页"、"引导流程"、"命名"、"职业选择"）。**不要把内部分类标签打印出来。**

* 仓库内："把这当作本代码库中的一个话题——关于 X。"
* 仓库外软件："把这当作本仓库之外的一个产品/软件话题——关于 X。"
* 非软件："把这当作一个[命名 | 叙事 | 商业 | 个人]话题——关于 X。"

不要规定纠正用语（"说 X 来切换"）。说明模式后继续；用户不同意会用自己的话纠正，届时重新分类并重跑受影响的路由。

**模式确实有歧义时主动确认。** 大多数在 0.2 确定的主题都能干净地分类——只在之后模式仍有真正歧义时才问（例如"我们的文档"可能是仓库文档，也可能是对外营销文档）。这时问一个阻塞问题，两个选项用平实语言说出两种理解（"当作本代码库的仓库文档" vs "当作对外营销文档"），不暴露内部模式名。

**非软件模式的路由。** 决策 2 = 非软件时：Phase 1 走仓库外扎根（用户材料综合 + 网络调研；尊重跳过用语；默认跳过经验检索），绝不做代码库扫描。然后读 `universal-ideation.md`，由它替代 Phase 2 的视角派发和 Phase 5 菜单——这一模式的领域无关视角、批判标准和收尾菜单只在那里定义。发想记录仍按 `post-ideation-workflow.md` Phase 4 自动写入。

## 0.4 材料检查（仅仓库外模式）

仓库模式跳过——仓库本身就是 Phase 1 代理的材料来源。仓库外模式（软件与非软件）下，Phase 1 代理依赖用户提供的材料。只有一句请求、没有描述、URL 或文件时，用户材料综合代理无从综合，网络调研的相关性也会变弱。

检验方法：把用户给出的某条背景换成一个截然相反的说法，会不会实质改变哪些想法能留下？会，说明材料已足够具体、能塑造想法，直接继续。不会，就问 1~3 个精心挑选的问题，重点是**补充材料，而不是描述主题特征**：

* 一个可以读取的 URL 或文件
* 一段对现状的简要描述
* 粘贴一份现有的草稿或简报

在用户已提供的内容上追问，不要从模板出发。默认用自由回答的问题；只有答案空间小而离散时才用单选。每次回答后重新检验，再决定是否继续问。用户给出敷衍回答（"不知道，直接开始"）时停止——把确实"没有材料"的回答当作真实答案，并在摘要中注明材料单薄，让 Phase 2 用更宽的生成来弥补。

**Surprise me 例外。** Surprise me 模式路由到仓库外软件主题时，材料是必需的，敷衍回答不可接受——套用 0.2 表中 `0.4 材料` 一行。

用户一开始就给了丰富材料（粘贴、简报、现有草稿、URL）时，用一句话确认理解，整个跳过这一步。

如果这一步实质改变了主题（不只是补充背景，而是换了主题），在派发 Phase 1 之前，针对新范围重跑 0.2 和 0.3——按实际要发想的内容分类，而不是按第一眼的范围。

## 0.5 解读关注点与数量

从参数和目前的问答中推断两件事：

* **关注点** —— 概念、路径、约束，或开放式
* **数量覆盖** —— 任何改变候选数或留存数的提示

默认数量：留下**5~7 个**想法。每个视角的目标数量，以及由此推出的原始数与去重后数量，由 `divergent-ideation.md` 定义。明确的覆盖要遵守，例如 `top 3`、`100 个点子`、`提高标准`。

有两个对称的深度覆盖，都由用户自己的措辞触发；默认值介于二者之间。

**`go deep`（或同义说法）—— 加码。** 所有发想代理提到最高档，Phase 2 的核实阅读预算加倍，Phase 3 增加第二个批判者。用户明确选择最高档成本，而不是从当前对话碰巧使用的模型继承。

**Tactical 信号 —— 减量。** 在关注点（和 0.2 的回答）中寻找 `打磨`、`typo`、`quick wins`、`小改进`、`清理`、`小修小补` 等措辞。出现时，说明用户选择了 tactical 范围，于是缩小这次运行：

* **减产量，不减代理。** 每个视角的目标从约 6~8 个降到 **3~4 个**，每个代理的核实阅读预算从 5 次降到 **2~3 次**。保持默认的代理与视角对应。成本主要在产出上，把每个视角的产出减半才是真正的节省；把多个视角塞进更少的代理，大多只是把同样的工作挪了位置。
* **不要为省钱把多个视角塞进一个代理。** 核实预算是**按代理计**，不是按视角计（见 `divergent-ideation.md`），一个代理负责三个视角时，每个想法得到的核实大约只剩三分之一——而无法核实的 `direct:` 依据正是本技能要防止的失败。省钱不能省在依据核查上。
* **Phase 1.5 最多 3 条轴，证据侦察最多 3 个。** 两个上限保持**相等**：侦察按轴一对一派发，超出侦察上限的轴进入生成时没有证据档案，只能引用 Phase 1 的概览。3 是拆轴的下限（再少就是不可拆），所以这是最小的一对联动上限，不能单独再减其中一边。
* **在两层都免除"值得开会讨论"门槛**——既对生成者，也在 Phase 3 依据核查者的派发提示中。核查者在全新上下文中运行，看不到生成过程，不告诉它就不知道门槛已免除。
* **保留依据核查，保留全部六个视角。** 便宜的运行也不能返回未经核查依据的想法；砍掉视角恰恰会去掉小主题仍然受益的那些不明显的想法。

按合理的理解来解读，不做形式化解析。

**Tactical 的全部调整项就是这些：** 每个视角 3~4 个想法；每个代理 2~3 次核实阅读；3 条轴；3 个侦察；两层都免除开会门槛。**Tactical 不改变其他任何东西**——不改代理数、不改视角集合、不改模型档位。下文与其他 reference 中"tactical 的调整项"就指这张清单，按名称引用，不重新罗列，避免多处漂移。

**检测到 tactical 信号不等于 tactical 范围生效。** 先解决覆盖之间的冲突；下游的一切——编队、调整项、各种免除——都以最终**生效**的状态为准，而不是以检测到的信号为准。`go deep` 直接压过 tactical 信号并完全取消它。tactical 信号与决定视角集合的模式（Issue 主题，或非软件路线的深度）冲突时，由该模式保留自己的视角与代理数，tactical 仍贡献它的调整项。

## 0.6 成本提示

派发 Phase 1 之前，用一行简短的话告诉用户成本构成，让多代理成本不被隐藏。说出本次实际会派发的扎根代理、发想编队的规模，以及跳过用语。例如：*"将派发：代码库扫描 + 经验检索 + 网络调研 + 最多 5 个证据侦察 + 5 个发想代理 + 1 个依据核查，大多在低档模型上。跳过用语：'不做外部调研'。"*

从本阶段已经做出的派发决定推出这行话，不要背一个固定总数。每个数字都在别处定义并可能变化：扎根由 Phase 1 的模式派发决定，侦察由 Phase 1.5 决定，发想编队由 `divergent-ideation.md` 决定，tactical 与 `go deep` 变体由 0.5 决定。只在刚刚推出了某个数时才说出数字；只列代理名、不给总数也可以。

适用时加上条件性的部分：Issue 分析增加一次扫描调用，**只有扫描返回可用信号时**才再加一次聚类调用；每份**大到需要提炼**的用户调研材料加一个提炼代理（小的直接并入扎根摘要，不占代理）；Phase 2 最多 2 个轴覆盖补派代理。用户说了跳过用语时减去网络调研——这一点现在就能从请求里看出来。

**本阶段还无法确定的，说"视情况"，不要预先减掉。** 网络调研缓存检查（`web-research-cache.md`）在 Phase 1 临时目录建好之后才进行，所以是否复用而跳过网络派发此时不可知。Issue 聚类调用和非软件模式下依深度而定的数量也是如此。

**某个数字取决于后续阶段的决定时——扫描结果、深度选择、尚未读取的派发规格——说出这一项并注明视情况，不要猜。** 拿平常的"5 个代理"去填这种空，是唯一肯定错的答案。

子代理不可用、将由主会话内联完成时，在这行话里一并说明：内联时各视角共享同一上下文，多样性和核查的独立性会下降。

这行话仅供知悉，用户无需确认。
