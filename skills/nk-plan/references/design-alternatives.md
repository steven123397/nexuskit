# 设计对比（Design It Twice）

阶段 1.6 满足条件时读本文件：一个后果重大、日后难以推翻的"怎么做"在调研后仍有两种以上站得住的结构。依据 Ousterhout 的"Design It Twice"：第一个想法往往不是最好的。

## 何时不做

* 用户、需求或代码库中已确立的写法已经**具体定下**了这个"怎么做"：不为了比较而重新打开它。产品方向定了，不等于没说明的技术选择也定了。
* 几个备选已经具体到可以直接比较：这需要判断而不是展开，直接在规划中比较并写进关键技术决策。
* 用户给了时间或预算限制、比较放不进去，或用户说"直接选一个"。

不做时说明原因，继续正常规划。

## 1. 界定问题空间

先写一段给用户看的问题说明：新接口或结构必须满足的约束；它依赖什么，以及这些依赖属于哪一类（见下）；一个粗略的示意片段，只用于让约束变具体，不是提案。展示后立即进入第 2 步。

**依赖分类**（决定这个设计怎么跨边界测试）：

1. **进程内**：纯计算、内存状态、无 I/O。直接通过新接口测试，不需要适配层。
2. **本地可替身**：有本地测试替身的依赖（内存数据库、内存文件系统）。带着替身测试，接口上不需要端口。
3. **远程但自有**：自己拥有的跨网络服务。在边界上定义端口，逻辑放在一个深模块里，传输作为适配器注入；测试用内存适配器，生产用 HTTP/gRPC/队列适配器。
4. **真正的外部**：无法控制的第三方服务。作为注入的端口，测试提供模拟适配器。

**边界纪律**：只有一个适配器的边界是假想的边界，至少有两个（通常是生产 + 测试）才值得引入端口；只为测试使用的内部边界不要暴露到接口上。

## 2. 并行展开备选

支持子代理时，并行派出 3 个以上子代理，每个给出一个**截然不同**的设计；否则在主会话中依次展开。每个子代理拿到一份独立的技术说明（文件路径、耦合细节、依赖类别、边界后面是什么），并附上 `CONCEPTS.md` 的术语，让命名与项目语言一致。给每个不同的设计约束：

* 设计 1："接口最小化——至多 1–3 个入口，每个入口的杠杆最大。"
* 设计 2："灵活性最大化——支持多种用法和扩展。"
* 设计 3："为最常见的调用方优化——让默认情况极其简单。"
* 设计 4（适用时）："围绕端口与适配器处理跨边界依赖。"

每个设计产出：接口（类型、方法、参数，以及不变量、顺序约束、错误模式）；调用方如何使用的示例；实现在边界后面隐藏了什么；依赖策略与适配器；取舍——杠杆在哪里高、在哪里薄。

## 3. 比较与推荐

依次展示各设计，再用文字比较：**深度**（接口上的杠杆）、**局部性**（改动集中在哪里）、**边界位置**。然后给出明确推荐——哪个最强、为什么；元素可以组合时提出混合方案。

## 4. 落入 plan

* 按 `../../conventions/decision-autonomy.md` 判断是否需要用户拍板：各设计的后果落在询问区（范围变化、不可逆、对外契约）或带来用户可见的行为差异时，把推荐方案和备选一起交给用户选择；否则采用推荐方案并记录理由。
* 选定结果写成关键技术决策：决策、否掉的备选、决定性的理由。用户参与了选择时按 [`../../conventions/settled-decisions.md`](../../conventions/settled-decisions.md) 加标注。
* 被选设计的接口与依赖策略体现在高层设计和相关单元的 Approach 中；引用对应 KTD，不重述。
* 比较不完整（例如某个方向没能展开）时如实写明，基于现有证据继续；只等用户偏好的决定写成 Open Questions 中的待决项。
