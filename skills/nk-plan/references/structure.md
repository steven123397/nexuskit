# 阶段 2–4：解决规划问题、划分结构、成文

建规划问题清单之前读本文件。plan 的章节、ID、frontmatter 以 `../../conventions/plan-format.md` 为准；本文件只补充"怎么写好"。

## 阶段 2：解决规划问题

从三处汇集问题：上游文档中推迟的问题；调研发现的缺口；产出可用 plan 所需的技术决策。

每个问题归为：
* **规划期解决**：答案可从仓库、文档或用户选择中得到；
* **推迟到实现**：答案取决于改代码、运行时行为或执行中的发现。

**只在答案实质影响架构、范围、顺序或风险，且无法合理推断时才问用户。** 提问遵循 `../../conventions/decision-autonomy.md`：互不依赖的问题合并为一轮（至多 3 个），每个给 2–3 个选项并标出 `(Recommended)`；有依赖关系时才分轮。自主决断区内的事（可逆、局部、有惯例可循）自己定，写进关键技术决策的理由。

**不重问已定决策。** 带 `session-settled:` 标注或按 [`../../conventions/settled-decisions.md`](../../conventions/settled-decisions.md) 判为已定的决策是已答输入。未经审视的指令在这里接受恰好一次以调研证据为依据的质疑，结果写成（带或不带标注的）关键技术决策。

**陌生领域用教学式提问**：用户表示不了解问题所在的领域（明确说"我不懂 X"，或之前的回答显示无法评估选项）时，不要光秃秃地提问：给出现实的选项、每项一句与本计划相关的取舍、一个推荐默认值。用户仍无法评估时，把默认值记为 plan 中的明确假设，而不是逼出一个猜测。无人值守时直接取推荐默认值并记为假设。

**不在此阶段**运行测试、构建应用或探测运行时行为。

**术语**：规划中敲定了新的领域术语，或发现用词与 `CONCEPTS.md` 冲突时，按 `../../conventions/concepts-vocabulary.md` 当场处理：冲突当面指出并对齐；合格的新术语立即写入 `CONCEPTS.md`（文件不存在时由第一个合格条目创建；整库初建属于 refresh 的职责，不在这里做）。

## 阶段 3：划分结构

### 3.1 标题与文件名

* 标题清楚可检索，以 ` - Plan` 结尾，不带 `feat:` 之类前缀（分类写在 `type`）。
* 文件名：`docs/plans/YYYY-MM-DD-HHMM-<type>-<3–5 个词的 kebab 描述>-plan.md`；`HHMM` 取写入时的本地时间，不分配每日序号。目录不存在就创建。路径冲突时在扩展名前加最小可用数字后缀（`-2`、`-3`），不覆盖。

### 3.2 受影响方

Standard 与 Deep 简要考虑谁受影响（终端用户、开发者、运维、其他团队），以及这如何影响计划；跨领域工作写进 System-Wide Impact。

### 3.3 划分实施单元

每个单元是一个有意义的改变，实施者通常能作为一次原子提交落地。粒度按实现内容划分：一个单元应能在一个会话内完成并独立验证。

好的单元：聚焦一个组件、行为或集成边界；通常只动一小簇相关文件；按依赖排序；具体到无需预写代码就能执行。避免：两三分钟的微步骤；横跨多个无关关注点；含糊到实施者还得自己发明计划。

### 3.4 高层技术设计

做法的形态靠文字说不清时——跨组件的架构、跨进程的顺序、状态机、分支关卡、生命周期、定量比较——加入高层技术设计，形式自选（组件图、时序图、泳道、流程图、状态机、决策矩阵、伪代码语法）。Markdown 中用 mermaid。只是一段话就能说清的模式套用时省略。

plan 中的图是与文字并列的权威内容，不加"仅为方向性示意"之类的免责说明；图文冲突时以文字为准。

**触发条件**（5.1 会核对）：3 个以上有方向关系的组件；3 步以上的协议；3 个以上状态的状态机；生命周期；3 个以上决策点；3 段以上的数据流；模式或开关的组合；DSL 或 API 接口设计；形态不明显的单组件。每类适用的触发条件至少对应一张草图。

### 3.4b 输出结构（可选）

新建目录结构的全新 plan（新插件、服务、包、模块），在新目录层级中新建 3 个以上文件、且目录布局本身是有意义的设计决定时，加 `## Output Structure` 文件树。它是范围声明而非约束，实施者可调整；各单元的 Files 仍是权威。只改已有文件或只新建一两个文件时省略。

### 3.5 定义每个单元

每个单元一个三级标题，带稳定 U-ID：`### U1. <名称>`。不写成列表项，不加 `- [ ]` 复选框（字段会脱离所属单元；进度以提交为准，不记在 plan 里）。

**稳定规则**：U-ID 一经分配不再改号。调整顺序时 ID 随单元移动（U1、U3、U5 的新顺序是对的，改成 U1、U2、U3 是错的）；拆分时原 ID 留给原概念，新单元取下一个未用编号；删除留下空号。深化时最容易误改号。

每个单元写：
* **Goal**：这个单元完成什么。
* **Requirements**：推进哪些需求或成功标准（引用 R-ID，上游提供时也引用 A/F/AE）。
* **Dependencies**：依赖哪些单元（用 U-ID）。
* **Files**：要新建、修改或测试的仓库相对路径。功能性单元写明测试文件路径。
* **Approach**：关键决定、数据流、组件边界、集成要点。**只写本单元特有的内容**，产品规则或协议引用对应 R/KTD，不重述。步骤或逐文件改动写成有序小列表。
* **Execution note**（可选）：只在单元需要非默认的顺序或验证方式时写一句自然语言，例如"先写请求/响应契约的失败集成测试""改这个遗留解析器前先补特征测试""主要是打包配置，以安装/运行冒烟验证为主"。不展开成 RED/GREEN/REFACTOR 子步骤。
* **Technical design**（可选）：做法不明显时的简短伪代码或图，注明是方向性示意。
* **Patterns to follow**：要参照的现有代码或约定。
* **Test scenarios**：逐条列出实施者应写的测试，每条写明输入、动作、预期结果，按单元的复杂度和风险定数量。考虑每个适用类别：
  * 正常路径——核心输入与输出；
  * 边界情况（有边界时）——边界值、空输入、空值、并发访问；
  * 错误与失败路径（有失败模式时）——非法输入、下游故障、超时、权限拒绝；
  * 集成场景（跨层时）——仅靠 mock 证明不了的行为，例如"创建 X 触发回调 Y 并持久化 Z"。
  直接落实某个上游验收示例的场景加前缀 `Covers AE<N>.`，只在确实对应时加。没有行为变化的单元（纯配置、脚手架、样式）写 `Test expectation: none -- <原因>`，不要留空。
* **Verification**：怎么判断单元完成，写成可观察的结果，不写 shell 脚本。

### 3.6 规划期未知与实现期未知分开

重要但此刻无法知道的内容（确切的方法名、接触真实代码后的最终查询、依赖实际测试失败才知道的运行时行为、开工后可能不再需要的重构），明确写进推迟到实现的问题，不假装已经解决。

### 3.7 防止范围膨胀

规划中发现的相邻重构、"顺手"清理、范围相邻的锦上添花，放进 Scope Boundaries 的 `#### Deferred to Follow-Up Work`，不放进实施单元。用户明确要求的除外。这不影响在已确认范围内"扩展还是新建"的判断，那仍由 Agent 决定并在确认环节展示。

## 阶段 4：成文

**本技能不写代码。** 所有深度用同一种规划方法，只改变详略，不改变规划与执行的边界。

### 4.1 按深度控制详略

* **Lightweight**：紧凑，通常 2–4 个单元，省略增值不大的可选章节。
* **Standard**：完整核心章节，省略对这次工作没价值的可选章节（包括高层设计），通常 3–6 个单元，相关时写风险、推迟问题和系统级影响。
* **Deep**：完整核心章节加必要的分析章节，通常 4–8 个单元，有助于清晰时把单元分组为阶段，写备选方案、文档影响和更深入的风险处理。

**Deep 可选扩展**（只在确实提高执行质量或对齐时加入）：Alternative Approaches Considered、Success Metrics（仅限产品成功标准没覆盖的运维指标：仪表盘、错误预算、告警阈值、发布遥测）、Dependencies / Prerequisites、Risk Analysis & Mitigation、Phased Delivery、Documentation Plan、Operational / Rollout Notes、确实影响当前设计的 Future Considerations。

**备选方案要比较"怎么做"**：架构、顺序、边界、集成方式、发布策略。细小的实现变体（用哪个哈希函数）属于关键技术决策；产品形态的备选（不同的参与者、不同的核心结果）属于 `nk-brainstorm`，不在这里重新讨论。

### 4.2 行文

* **先写结论**：先写决定或结果，再写理由，再写背景；一段一个论点及其支撑。Summary 只写提议，Problem Frame 只写动机，两者不互相重复。
* **Summary 是几句话**，不是一个带五个分号和四个括号的长句。关键技术决策的理由写决定性的那个理由，不是所有理由。
* **一个需求或单元是一句意图加至多一个限定**。要写"A 或 B，由实施者决定"时，只写意图，把分叉放进 Open Questions。
* **精确不是冗余**：文件路径、ID、日期、领域术语、条件、确切阈值原样保留；能确定具体锚点时用具体锚点，不用含糊的抽象。
* **一条规则只在一处写全**：产品行为写在 R 上，实现机制写在 KTD 上，其他地方引用 ID 并只补充本处特有的内容。没有 ID 链接的平行重述是缺陷。引用外部权威文档时写承诺和路径，只记录本工作的差异，不写多句摘要。
* **就地改写**：新决定取代旧文字时直接改写或删除，不留删除线、不另起"补充说明"层。执行期的范围或做法变化记在 `## Change Log`（见 plan-format）。
* **成文前的检验**：实施者能否一遍读出每节里的矛盾？没参加对话的同事只读 Objective 能否说出这项工作是什么？一个句子超过一个括号说明、串起两个以上分号、一个条目规定两个结果、或同一条规则在多处写全，都要拆开、推迟，或改成引用。

### 4.3 Markdown 写法

plan-format 之外的呈现原则：

* 不按固定列宽硬换行；每段一行或每句一行。
* 不混入 HTML。唯一例外是约定的不可见语义标记（如 `nk-brainstorm` 写入的 `<!-- nk-section: work-relationships -->`），它为下游 Agent 标明章节含义、不影响版式，保留原样。
* 内容形态决定呈现：叙述性内容（动机、决策理由、问题背景）用段落；3–5 个各带几行说明的平行项用要点；5 个以上结构一致的项用表格。
* 要点有子结构时用加粗的前导标签（例如流程的 **Trigger:** / **Actors:** / **Steps:** / **Covered by:**），不用更深的标题层级。
* Standard 与 Deep 的顶层章节之间用 `---` 分隔；一屏能放下的 Lightweight 省略。
* 需求跨越多个关注点时，按能力分组（加粗的组名），R-ID 跨组连续编号，不在每组从 R1 重新开始。
* 验证与完成标准中，命令、适用范围、单元与完成信号形状一致时用表格；写本仓库的具体命令。

### 4.4 规划规则

* 所有文件路径都是仓库相对路径。plan 针对另一个仓库时，在顶部写一次 `**Target repo:** <名称>`，全文仍用仓库相对路径。
* 优先写"路径 + 类/组件/写法"引用，少用容易失效的行号。
* 不写实现代码：没有 import、确切的方法签名或框架特有语法。高层设计和单元的技术设计字段中可以有伪代码和 DSL 草图，注明是方向性示意。
* 数据模型改动用 ERD，多服务交互用时序图，生命周期用状态图，复杂分支用流程图——在它们确实让关系更清楚时使用。
* 不写 git 命令、提交信息或单元级的测试命令编排（本仓库的具体验证命令写在 Verification Contract）。
* 不为了让 plan 看起来完整而假装解决了实现期问题。
* 不记录规划过程（"在第几阶段得出"），不写指向下一个技能的 `## Next Steps`。
