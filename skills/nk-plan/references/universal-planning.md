# 非软件规划

阶段 0.1b 判定为非软件任务时读本文件。它取代软件规划的 0.2 到 5.1。

## 开始前核对分类

* **其实是软件任务吗？** 按任务类型区分，不按话题：关于 Rust 的学习指南是非软件（产出教学内容），Rust 库的重构是软件（改代码）。是软件就回到 `phase-0.md` 的 0.2。
* **是只需一个事实就能回答的问题吗？** 只有无需检索、调研或判断就能一句话回答的问题才直接回答并结束，用用户的话回答，不解释"这不是规划任务"之类的路由过程。需要多步、检索或综合的问题属于回答型任务（见下），不属于这一类。拿不准就不走这个出口。
* **产物标注**：非软件规划的产出不写 `plan_contract: nk-plan/v1`，除非交付物本身就是完整的软件实施 plan。

核对完就全力完成任务，不因为它"看起来像查询"而放弃。然后选择下面的处理方式。

---

## 处理方式：要一份计划，还是要一个答案

* **要计划**：交付物是计划本身，如旅行行程、学习大纲、活动执行手册、项目计划。按下面第 1–3 步。
* **要答案**：交付物是答案，例如调查或分析性的问题（"X 多久发生一次，严重吗？""我们的做法和 Y 比怎么样？""要不要做 Z？"）。计划只是得到好答案的手段。按下面的**回答型流程**，跳过第 3 步的存档。

两者兼有（"先调研 X，再规划 Y"）时，先做回答型调研，再产出计划。选定一种就只走那一条。

---

## 回答型流程

规划的直觉仍然适用，但计划只是**临时脚手架**：在聊天中说明、用来引导工作、展示思路，执行完即丢弃，不写计划文件。

**先说行动计划，然后直接做**：按问题大小说明怎么回答——轻量问题一行，多方面的分析问题几条要点。这一步**不阻塞**：说明后立即继续，不请用户批准；只在遇到无法自行判断的真正分歧时才问（例如"他的个人账号还是组织账号？"）。

**执行**：答案依赖模型记不准的事实（最新数据、近期事件、会变动的细节）时，用下面第 1 步的调研拆分法收集。模型熟悉的内容不必调研。**涉及用户自己的代码、仓库或点名的产物时，以实际来源为准，不凭记忆**：先读再答。这里的执行只限调研与分析，读代码理解它可以，写代码或运行代码改变系统不行，那属于 `nk-work`。

**给出答案**：在聊天中回答。默认不写文件、不出存档菜单。调研产出了用户可能想保留的东西（对比表、带来源的摘要）时，提议保存。无人值守时跳过提议，直接回答。

**展示什么、隐藏什么**：像专业顾问一样只讲与用户问题相关的思考。
* **展示**：针对用户问题的做法，用用户的话。
* **隐藏**：正在运行哪个技能、哪个模式、哪个阶段；写没写计划文件；路由决定本身。
* **永远不隐藏**：影响答案可信度的限制、缺口和不确定性（"我只能拉到他最近约 100 个 star，所以结论不完整"）。

---

## 第 1 步：评估模糊性与调研需要

**问 1–3 个问题会显著改善计划吗？** 答案会改变计划的结构或内容时，默认问 1–3 个（见第 1b 步），并总是附一个"跳过——按合理假设直接做"的选项。请求已经给全主要变量、或任务简单到合理假设就够时，不问。

**计划是否依赖变化快于训练数据的事实？**

| 调研需要 | 信号 | 处理 |
| :-- | :-- | :-- |
| **无** | 通用、不随时间变化或概念性的计划（学习方法、项目管理方法、个人目标拆解） | 不调研。成稿后提议："这份计划基于一般知识，要不要我查一下 [调研能改善的具体内容]？"用户同意才做 |
| **建议** | 计划涉及具体地点、场所、日期、价格、时刻表、季节性、时事——过时信息会让计划失效 | 先调研再规划：拆成 2–5 个聚焦的调研问题并行检索，整理后再成形 |

需要调研就去做，不要只给免责声明。

**调研拆分法**：列出 2–5 个相互独立、模型最没把握的问题（当前价格、营业时间、可用性、近期变化、季节细节）；优先用用户点名的来源，覆盖不到的用网络检索；支持子代理时并行派出（可用较便宜的模型），否则依次进行；整理成简短调研摘要再规划。

## 第 1b 步：聚焦提问

最多 3 个问题，针对最能改变计划的未知项，一轮问完（遵循 `../../conventions/decision-autonomy.md`）。

* 给出有依据的选项，而不是空白提问："工作日排队时间短 30–40%，你的时间灵活吗？"比"你什么时候去？"好。
* 多个独立选择可以合并为一个多选题。
* 总是附"跳过——按合理假设直接做"。超过 3 个就不再问，其余按假设处理。

## 第 2 步：成形

不使用软件 plan 模板（没有实施单元、测试场景、文件路径）。

**给方案还是给选项**：

| 任务类型 | 形式 | 原因 |
| :-- | :-- | :-- |
| 个人偏好强（吃、玩、礼物） | 每类给 2–3 个精选选项，让用户组合 | 偏好因人而异，单一选择容易不合心意 |
| 逻辑有先后（学习计划、项目时间线、多日行程） | 单一明确路径，顺序清楚 | 顺序重要，每步都给选项会让人难以决定 |
| 混合（固定结构、细节可变的活动） | 固定骨架，标出选择点 | 骨架定了，具体场地或内容可选 |

**格式**：可执行的内容（步骤、选项、后勤、预算）用要点和表格；只有背景、理由和串联说明用段落。

**质量原则**：步骤具体到无需再调研就能执行；按依赖排序；需要时写明时间、时长、截止点；写明所需资源；重要决策写明备选或变化时怎么办；详略与任务复杂度相称；格式贴合领域（行程、大纲、执行手册、项目计划、调研计划、选项菜单）。

## 第 3 步：交付

按提问规则问用户怎么接收："计划好了，你想怎么接收？"

1. **保存到磁盘**：询问位置——`docs/plans/`（仅当该目录存在时列出）、当前工作目录、系统临时目录、自定义路径。文件名 `YYYY-MM-DD-HHMM-<描述>-plan.md`（`HHMM` 取写入时的本地时间，冲突时加最小可用数字后缀，不覆盖）。文件以 `# 标题` 开头，下一行 `Created: YYYY-MM-DD`，不写 YAML frontmatter。
2. **只在聊天中保留**：不写文件。

不提供 `nk-work`（仅限软件）和创建 Issue（不适用于非软件计划）。
