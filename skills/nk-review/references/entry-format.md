# 审查条目格式（`docs/reviews/`）

审查记录的写入格式契约。`nk-close` 收尾时靠本文件的固定状态标记甄别遗留项，字段名与状态词表不得自由发挥。

## 文件组织

- 默认**每个版本一个文件**：`docs/reviews/<版本或分支标识>.md`（如 `docs/reviews/v2.0-parser.md` 或 `docs/reviews/feat-export.md`）。同一版本的多轮审查向同一文件追加，不另建新文件。
- 标识取当前版本号或分支名；目标项目工作流文档另有规定的从其规定。

## 文件头部

```markdown
# 审查记录：<版本或分支标识>

- **范围**：<基线 ref> -> HEAD（<N> 个文件，约 <M> 行可执行改动）
- **意图**：<一两句话：本次变更要达成什么>
- **审查轮次**：第 1 轮 2026-09-26
- **概要**：待修 3 / 已修复 5 / 遗留-转 Issue 1
```

概要计数随条目状态变化同步刷新；它是文件的实时索引，不是历史快照。

## 条目格式

每个发现一个小节，字段齐全才算一条合格条目：

```markdown
### [R1-F03] P1 · 待修 · 导出结果集无分页
- **位置**：`app/services/export_service.rb:87`
- **来源**：performance（置信度 100）
- **问题**：`Order.where(...).to_a` 一次性物化全部结果集，大账户会让 worker 内存溢出。
- **建议**：改用 `find_each` 流式处理，或先定分页契约。
- **证据**：`export_service.rb:87 -- orders = Order.where(account: account).to_a`
```

字段规则：

- **编号**：`R<轮次>-F<序号>`，文件内唯一。编号在复核定稿后一次性分配，之后**永不重排**；后续轮次引用旧条目时用原编号。
- **严重级别**：`P0`（阻断，合并前必须处理）/ `P1`（应当修复）/ `P2`（值得修复）/ `P3`（低信号）。
- **状态标记**：标题行 `·` 分隔的第三段，词表固定为三值——`待修` / `已修复` / `遗留-转 Issue`。`nk-close` 以此甄别遗留项，不使用其他措辞（如"已解决""搁置"）。
- **位置**：`file:line`，指向具体行；跨文件的在问题描述中补述。
- **来源**：产出该发现的 persona 名与置信度锚点（50/75/100）；多个 persona 命中同一问题并列署名。
- **问题**：先写可观察的外部后果（用户、调用方、运维会看到什么），再点机制；2~4 句。
- **建议**：具体可执行的修法；能从仓库既有模式出发就点名参照位置。确实没有代码层面建议时（纯决策问题）写明需要的输入。
- **证据**：置信度 75/100 的条目首条证据必须是使问题成立的原文行（含 `file:line`）；置信度 50 的条目说明缺什么证据。

## 多轮追加规则

新一轮审查在文件末尾追加区块：

```markdown
## 第 2 轮（2026-09-28，范围：<本轮 diff 说明>）

### [R2-F01] ...
```

- 新条目用新一轮编号；复核旧条目时**就地更新其状态行与概要计数**，不为状态变化新建条目。
- 复检确认已修复的条目，状态改为 `已修复`，可在条目末追加一行修复提交哈希，便于追溯。
- 决定不修、推迟到后续版本的条目，状态改为 `遗留-转 Issue` 并注明 Issue 编号（无远端时为 `docs/backlog.md` 条目）。

## 状态更新纪律

条目状态的更新（待修 -> 已修复 / 遗留-转 Issue）不单独发起提交：随修复代码的提交一同入库（[`../../conventions/commit-cadence.md`](../../conventions/commit-cadence.md) R2；一组修复时统一附在最后一个修复提交，R6）。本技能自身也不发起提交，新建的审查记录文件留在工作区，随下一个代码提交或会话交接提交入库。

## 行文与排版规则

- 不粘贴大段代码或整段 diff，一律引用 `file:line`；条目内引用代码不超过一两行。
- 表格中若出现字面 `|`（代码片段、正则、分隔符示例），写成 `\|`。
- 覆盖说明写在当轮区块末尾一行：跳过条件命中的 persona 及原因、未跟踪文件排除清单、未验证项。审查结论里没跑到的东西要能被读者看见。

## 聊天内汇报格式

写文件之外，在聊天中给用户一份浓缩摘要（不落盘）：

```markdown
> **结论**：可合并 / 修复后可合并 / 存在阻断项
>
> **理由**：<一两句>
>
> **修复顺序**：P0 -> P1 ->（顺手的 P2）
```

摘要前列出按严重度分组的条目速览（编号 + 位置 + 一句话问题），并指向审查记录文件路径。零发现是合法结果：文件照写（记录范围与零发现结论），摘要直说未发现需要处理的问题。
