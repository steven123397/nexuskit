# 实施循环与证据策略 (Implementation Loop)

> **路径解析说明：** 本文件中引用的共享约定（如 `../../conventions/`）均相对于本文件所在目录解析。

本文件规范 `/nk-work` 中实施单元的标准推进循环、测试发现、证据策略与系统级因果检查。

---

## 一、已完成检查与前置准备

### 1. 已完成检查 (Already-Done Check)
在动手修改前，先核查代码库现状：
* 若本单元的完成信号完全来自代码库内部，且当前代码已具备预期能力、满足验证标准（可能已在先前分支或会话中交付），运行测试核实后直接视为完成，不重复编码。
* 若完成标志涉及仓库外状态，按 [`out-of-repo-state.md`](out-of-repo-state.md) 处理。

### 2. 风格对齐与批量只读检索
* 优先阅读 Plan 中引用的参考文件，对齐既有代码的命名惯例、错误处理与目录结构，复用现有组件。
* 将互不依赖的只读操作（参考文件读取、模式检索、测试文件查找）合并在同一轮执行，提高效率。

## 二、测试发现与证据策略 (Test Discovery & Evidence Strategy)

### 1. 测试发现 (Test Discovery)
在修改实现文件前，检索其对应的现有测试文件（按导入引用或命名模式查找）。若 Plan 已列出测试文件或场景，以此为起点并检查是否有未列出的关联测试。

### 2. 证据策略表（按已有测试状况划分）
根据测试发现的结果，在修改生产代码前选定本次任务的证据策略：

| 已有测试的状况 | 应采取的行动 |
| :-- | :-- |
| **已有测试已经因目标行为而失败** | 直接将该测试作为变红（Red）证据；**不新增重复的测试** |
| **已有测试覆盖了该契约，但断言的是旧行为或错误期望** | 修改该现有测试，运行并确认其在写实现前按预期失败 |
| **已有测试 Mock 过度或漏掉了真实调用链** | 针对性地加强或重构该测试，确认其因正确的原因失败 |
| **尚无任何现有测试覆盖该行为** | 新增最小聚焦的失败测试或特征测试（Characterization Test） |
| **任务本身不适合编写自动化测试** | 记录无测试豁免理由与替代验证方案，验证通过后方可完成 |

### 3. 测试场景完整性检查 (Test Scenario Completeness)
在编写测试前，检查 Plan 的测试场景是否覆盖以下适用类别；若缺失或表述含糊（如仅写“验证正确”而无输入输出），先结合单元上下文补全：

| 场景类别 | 适用时机 | 缺失时的推导方法 |
| :-- | :-- | :-- |
| **正常路径 (Happy path)** | 所有功能性单元必选 | 从单元目标与方案中提取核心输入/预期输出对 |
| **边界情况 (Edge cases)** | 存在输入边界、状态切换或并发时 | 识别极值、空值/Nil 输入及并发访问模式 |
| **错误/失败路径 (Error paths)** | 存在校验、外部调用或权限控制时 | 枚举应拒绝的非法输入、权限拒绝及下游故障处理 |
| **集成场景 (Integration)** | 跨越多个层级（回调、中间件、多服务）时 | 识别跨层调用链，编写不使用 Mock 的真实穿透场景 |

## 三、执行证据守则与推进节奏

### 1. 执行证据守则 (Guardrails for Execution Evidence)
* **不在同一步同时写出测试和实现**：执行测试先行时，先写测试并观察失败，再写生产代码。
* **确认因预期原因变红**：不跳过对新增或修改测试的失败验证。
* **不超越当前切片过度实现**：每次只实现让当前失败测试变绿所需的最小行为切片。
* **不新增重复回归测试**：当现有测试文件就是合适归宿时，直接更新或加强它，不另起炉灶制造冗余。
* **测试必须检验真实行为而非实现细节**：测试应在行为破损时变红、仅重构内部实现时保持常绿。若期望值直接取自被测代码自身、或由 Mock 直接提供被测结果、或仅断言内部方法调用次数而非边界输出，均视为无效测试。
* **不为测试污染生产代码**：当真实入口可以驱动行为时，不在生产代码中专门添加仅供测试使用的导出（export）、开关（flag）、包装器或钩子。
* **豁免需留痕**：琐碎重命名、纯配置、纯样式、生成物及纯手动界面可豁免测试先行，但需记录原因及替代验证结果。

### 2. 红绿推进与持续测试节奏
* **垂直切片循环（Red -> Green）**：每轮自选一个接缝（Seam，见 [`testing.md`](testing.md)），写一个失败测试 -> 运行确认变红 -> 写最小实现 -> 运行确认变绿。（注：**循环内不做 Refactor 重构精简**，遵循 Matt 原生纪律与 P1 范围约定）。
* **分层持续运行**：循环中途频繁运行当前单个测试文件与类型/编译检查；单元收尾时运行关联测试套件与全量受影响测试，出现失败立即修复。

## 四、系统级因果检查与收尾核对

### 1. 系统级因果 5 问 (System-Wide Test Check)
在宣告单元完成前，暂停并回答以下 5 个系统级问题：

| 系统级问题 | 核查动作 |
| :-- | :-- |
| **a. 这段代码运行时会触发什么？**（回调、中间件、观察者、事件处理器——从改动处往外追两层） | 阅读真实代码（而非仅看文档），核查所触碰模型上的回调、请求链中间件及后置钩子 |
| **b. 测试有没有走真实的调用链？**（若所有依赖都被 Mock，测试仅证明了孤立逻辑，未验证交互） | 至少编写一个使用真实对象穿过完整回调/中间件链的集成测试，交互层之间不使用 Mock |
| **c. 失败时会不会留下孤立的状态？**（若在调用外部服务前持久化了数据库行、缓存或文件，外部失败或重试时会怎样？） | 追踪真实对象的失败路径；若风险调用前已创建状态，测试失败清理逻辑或重试幂等性 |
| **d. 还有哪些接口暴露了同一行为？**（Mixin、DSL、平行入口点） | 在相关模块检索同类方法或行为；若需保持一致，当场补齐，不留作后续遗留 |
| **e. 各层的错误处理策略是否冲突？**（重试中间件 + 应用层降级 + 框架异常捕获是否导致重复执行或吞掉错误？） | 列出各层具体的错误类型，确认上层捕获列表与下层实际抛出的异常严格匹配 |

* **何时可跳过**：无回调、无状态持久化、无平行接口的纯叶节点改动（如新增纯辅助函数），10 秒确认“无外溢触发”即可跳过。

### 2. 常规收尾清单
* 相关测试均已在终端实际运行并获得通过证据（未运行项如实标记为“未验证”）；
* 无新增编译器警告、类型错误或 Lint 报错；
* 对外契约符合 [`../../conventions/decision-autonomy.md`](../../conventions/decision-autonomy.md) 约束；
* 已清理所有临时调试代码（如 `console.log`、`dbg!`、`print`）。

## 五、已定决策规则 (Settled Decisions)

* Plan 或需求文档中已明确标注为用户敲定（如 `session-settled`、`user-directed`、`user-approved`）的技术或产品决策，属于用户已做出的定论，**执行者不应在实现中擅自“改进”或推翻**。
* Plan 未作限定、留待实现时决定的细节，由 Agent 按自主决策规则裁量。
* 若在编码实现中发现某项已定决策确实不可行、存在破坏性或与事实严重冲突，将其作为真实阻断项（Blocker）报告给用户，而不静默绕过或暗自修改方案。
